\paragraph{The Kernel Driver}

\paragraph{Device-Side Execution}

The GPU device executes computations via user-defined device kernels and proprietary vendor firmware, which are compiled into static binaries specifying precise thread-level SIMT behaviors. GPU hardware schedulers manage thread execution at warp granularity. Device-internal state, including per-warp access patterns, SM utilization, and thread-block progress, is not exposed to host-side drivers.

\subsection{eBPF and Kernel Extensibility}
\label{sec:background}

% Moved from "Limitations" — CPU eBPF paragraph, reframed as background on eBPF
eBPF (extended Berkeley Packet Filter) allows user-supplied programs to run safely inside the OS kernel. Programs are statically verified at load time for termination, memory safety, and type correctness, then JIT-compiled to native code. The verifier guarantees that programs access only permitted memory regions and call only approved kernel functions (helper or kfuncs). Programs attach to kernel-defined hook points, where the kernel invokes BPF callbacks at specific decision points and falls back to default behavior if no program is loaded. This mechanism has enabled runtime-programmable extensions to kernel subsystems: \texttt{sched\_ext}~\cite{schedext-docs} makes CPU scheduling programmable, \texttt{cache\_ext}~\cite{zussman2025cache_ext} extends page cache eviction, and XDP processes packets at the driver level.

\subsection{The Diversity of GPU-Centric Workloads}

Modern GPU systems run diverse workloads whose conflicting resource demands require different management policies.
LLM inference alternates between compute-intensive prefill and bandwidth-bound decoding~\cite{zhong2024distserve,patel2024splitwise}, with irregular KV-cache offloading~\cite{sheng2023flexgen,kwon2023efficient} and sparse MoE expert activations~\cite{gale2023megablocks,he2021fastmoe} that benefit from expert-aware eviction and stride-based prefetching; the default LRU eviction and tree-based prefetching in the driver perform poorly.
GNN training exhibits irregular, pointer-chasing accesses~\cite{lin2024towards,wang2016gunrock} where aggressive sequential prefetching helps, yet the same strategy harms random-access workloads.
Vector search has two distinct phases: index construction scans data sequentially, while query traversal follows random access patterns~\cite{pan2024survey,cao2023gpu}, requiring phase-adaptive prefetch policies.
These distinct memory behaviors (\Cref{fig:access_patterns}) and imbalanced thread scheduling across SMs (\Cref{fig:thread_scheduling}) demonstrate that no single eviction, prefetch, or scheduling policy fits all workloads. Moreover, optimal policies change at runtime: vector search alternates phases, multi-tenant mixes shift as jobs arrive and depart, and oversubscription ratios vary dynamically, making static policy selection at deploy time insufficient. In multi-tenant environments, latency-critical inference conflicts with throughput-maximizing training, creating contention that per-tenant priority differentiation can resolve but fixed partitioning cannot~\cite{xiao2018gandiva,yu2020fine}.

\subsection{Agent-Based Policy Exploration}
\label{sec:motivation-agent}

AI agents are increasingly capable of generating system policy code, not merely tuning configurations. Recent work demonstrates agents generating compiler heuristics~\cite{alphaevolve2025}, datacenter scheduling and LLM serving code~\cite{hamadanian2025glia,cheng2025barbarians}, and eBPF policies for congestion control and CPU scheduling~\cite{dwivedula2025policysmith,zheng2025schedcp}. GPU resource management, with its large policy space and workload-dependent optima, is a natural target for such exploration.

To be effective in this domain, agents require an interface that is dynamic, programmable and safe. This policy interface benefits human developers as well, but agents amplify the need by exploring at a pace where manual safety review become harder. Programmable, because agents generate policy \emph{code} (e.g., eviction ordering functions, prefetch strategies), not parameter vectors; fixed configuration knobs cannot express what agents produce. Safe, because agents explore iteratively, generating tens to hundreds of candidate policies, some of which may be incorrect; the interface must contain errors without crashing the kernel or corrupting device state. Fast iteration is equally important: loading a new policy should take milliseconds, not require rebuilding or reloading kernel modules. No existing GPU policy interface provides all three properties (\S\ref{sec:motivation-limitations}).

\subsection{GPU-Specific Challenges for Policy Extensibility}
\label{sec:motivation-challenges}

Beyond the need for a dynamic, programmable, and safe interface (\S\ref{sec:motivation-agent}), three properties of GPU architecture pose challenges that have no counterpart in CPU extensibility:

\paragraph{Cross-device latency.} Operations that cross the host-device boundary, such as page migration and context preemption, require milliseconds of DMA across PCIe, far exceeding the microsecond budget of a synchronous kernel callback. Policies must therefore initiate transitions asynchronously and act proactively from application-level triggers, not only reactively at the fault that reveals the need.

\paragraph{Memory-scheduling coupling.} Limited device memory creates tight coupling between memory placement and compute scheduling: which data is resident directly determines which workloads can execute, and a page fault is simultaneously a memory event and a scheduling stall. Unlike CPU systems where scheduling (sched\_ext) and memory management (cache\_ext) are independent subsystems, GPU policies must coordinate across both domains simultaneously.

\paragraph{Device opacity.} The GPU's distinct ISA and execution model make device-internal state, such as per-warp access patterns, SM utilization, and thread-block progress, invisible to host-side software. Effective policies require observation of this state, yet no existing host-side mechanism can provide it.

\label{sec:motivation-limitations}

Existing approaches each fail to provide a dynamic, programmable, and safe interface that addresses these challenges:

\paragraph{Driver-Level Kernel-Space Policies.}

Systems like TimeGraph~\cite{kato2011timegraph}, Gdev~\cite{kato2012gdev}, GPREEMPT~\cite{fan2025gpreempt}, LithOS~\cite{coppock2025lithos}, GCAPS~\cite{wang2024gcaps}, and kernel interception methods~\cite{kernelintercept} embed customized scheduling and memory-management logic into kernel-space or user-space driver modules. Despite improved performance, these approaches embed static policies requiring kernel modifications to change, making them neither safely iterable nor rapidly deployable. They also cannot express asynchronous policies to handle cross-device latency (\S\ref{sec:motivation-challenges}).

\paragraph{Host User-Space Runtimes and Libraries}
Recent frameworks~\cite{ng2023paella,gim2025pie,shen2025xsched,chen2025ktransformers,coppock2025lithos} expose programmable GPU scheduling and memory management at the user-space layer. Despite this programmability, user-space systems share three limitations.
First, programmability remains application-bound: developers must write policies for a specific framework or runtime, often requiring code changes or porting applications onto specialized stacks, preventing reuse across ecosystems.
Second, user-space runtimes, confined to isolated process silos, lack global visibility across the coupled memory-scheduling domains (\S\ref{sec:motivation-challenges}) and cannot coordinate across multi-tenant environments~\cite{xiao2018gandiva,yu2020fine}. Hardware partitioning such as NVIDIA's Multi-Instance GPU (MIG) imposes fixed resource boundaries that cannot be dynamically rebalanced.
Third, user-space frameworks lack privileged access to low-level driver mechanisms, leaving policies constrained to coarse-grained GPU kernel launch boundaries. This precludes precise preemption for latency-sensitive tasks and prevents fine-grained compute-transfer overlap. Moreover, they cannot execute policy logic on latency-critical paths (e.g., page-fault handlers), nor exploit GPU-side warp-level or barrier-level access patterns.

\paragraph{Binary Instrumentation and Profiling Tools on Device}
Tools such as NVBit~\cite{villa2019nvbit} and Neutrino~\cite{neutrino} address device opacity (\S\ref{sec:motivation-challenges}) by injecting logic directly into GPU binaries. NVBit supports dynamic SASS-level instrumentation, while Neutrino provides instruction-level profiling via programmable assembly-layer probes with an eBPF-like interface. Despite this device-side visibility, these tools lack safety guarantees (injected logic can cause crashes or deadlocks), target offline profiling rather than online policy enforcement, and cannot coordinate policies across processes or with host-side drivers. A prior workshop paper eGPU~\cite{egpu} extends eBPF to GPU instrumentation but remains limited to read-only observability with prohibitive overhead (see \S\ref{sec:eval}).

\paragraph{Host-Side eBPF Extensibility}
CPU-side eBPF extensibility (\S\ref{sec:background}) does not directly extend to GPUs. Host-based eBPF treats the GPU as a black box: it can trace driver commands but cannot observe device-internal execution state (e.g., warp divergence), preventing reaction to on-chip bottlenecks. Furthermore, unlike the Linux CPU scheduler refactored to support \texttt{sched\_ext}, monolithic GPU drivers expose no safe programmable extension points. Their resource management mechanisms are tightly coupled to low-level hardware interactions (e.g., MMU invalidation), and naively exposing such controls risks resource leaks, hardware hangs, or kernel panics.

\medskip
\noindent In summary, no existing approach provides a GPU resource management interface that is simultaneously programmable, safe for iterative exploration, and capable of addressing the cross-device latency, memory-scheduling coupling, and device opacity inherent in GPU systems.

\section{Background and Motivation}

\subsection{The Diversity of GPU-Centric Workloads}
% \xiangyu{Workloads in CPU clusters}

Modern GPU-centric systems, ranging from single-node dense servers to disaggregated clusters, host heterogeneous workloads with fundamentally conflicting resource requirements. Generative AI inference pipelines are increasingly complex: Prefill-Decode disaggregation separates compute-intensive prompt processing from bandwidth-bound token generation across networked nodes~\cite{zhong2024distserve,patel2024splitwise}; KV-cache offloading alternates between transfer-intensive and memory-bound phases~\cite{sheng2023flexgen,kwon2023efficient}; Mixture-of-Experts (MoE) models generate sparse activations necessitating frequent paging of expert weights~\cite{gale2023megablocks,he2021fastmoe}. Neural network training is equally diverse: dense distributed training relies on predictable synchronization, whereas Graph Neural Network (GNN) training and sparse embedding lookups exhibit irregular pointer-chasing accesses that defy hardware prefetching. Vector search workloads further add variability: HNSW indexing demands random access, while IVF indexing emphasizes high-throughput sequential scanning. \Cref{fig:access_patterns} visually highlights such distinct memory access behaviors through page fault tracing, underscoring that static memory management policies cannot optimally serve all workloads. Similarly, GPU thread scheduling also shows substantial variability and imbalance (\Cref{fig:thread_scheduling}), with uneven load distribution across SMs and warps. This unpredictable scheduling behavior, invisible to conventional profiling tools, motivates fine-grained, programmable GPU observability.

\paragraph{User-Space Logic (Applications \& Runtimes)}
% userspace include 2 parts: runtime and application. discuss them separately.
High-level frameworks (e.g., PyTorch) and runtimes (e.g., CUDA libraries) operate entirely in user space, managing operation graphs, tensor layouts, and command submissions via memory-mapped interfaces or ioctl calls to drivers. These user-space components encode rich semantic information, such as neural network structures and latency constraints. Runtime systems like vLLM~\cite{kwon2023efficient}, fine-grained sharing frameworks such as Salus~\cite{salus}, and UVM-focused runtimes like PILOT~\cite{pilot} also implement sophisticated resource management policies in application-specific user-space logic.

\paragraph{The One-size-fits-all Kernel Driver}
The GPU driver acts as the OS component for GPU systems, managing privileged low-level hardware mechanisms including the Memory Management Unit (MMU), hardware interrupts, and kernel scheduling. Typical drivers are monolithic, implementing generic, application-agnostic resource-management algorithms such as Least Recently Used (LRU)-based page eviction, simple round-robin scheduling for context switching, and basic tree-based prefetching mechanisms in Unified Virtual Memory scenarios. These drivers traditionally offer coarse-grained policies, intentionally abstracting away application-specific semantics.

\paragraph{Device-Side Execution}

The GPU device executes computations via user-defined device kernels and proprietary vendor firmware, which are compiled into static binaries specifying precise thread-level SIMT behaviors. GPU hardware schedulers manage thread execution at warp granularity. Device kernels and firmware lack runtime adaptability, making critical internal states—such as warp divergence, cache thrashing, and thread-level execution bottlenecks—completely opaque to host-side drivers. This architectural opacity severely constrains host-driven, runtime workload-adaptive optimization opportunities.

In summary, modern GPU software stacks are characterized by a tight coupling between resource-management mechanisms (memory migration, kernel scheduling, and event tracing) and rigid, statically-defined policy logic embedded within kernel drivers, closed-source firmware, and statically-compiled device kernels. This architectural coupling significantly limits runtime policy flexibility, programmability, and adaptability in modern GPU-centric infrastructures.

\subsection{Limitations of Existing Extensibility Mechanisms}

Existing approaches attempting to mitigate the rigidity described above fall broadly into four categories, each facing fundamental limitations:

\paragraph{Driver-Level Kernel-Space Policies.}

Recent research has introduced driver-level resource control by moving policy decisions into kernel drivers or intercepting driver-level events. Systems like TimeGraph~\cite{kato2011timegraph}, Gdev~\cite{kato2012gdev}, GPREEMPT~\cite{gpreempt}, LithOS~\cite{lithos}, GCAPS~\cite{wang2024gcaps}, and kernel interception methods~\cite{kernelintercept} embed customized scheduling and memory-management logic into kernel-space or user-space driver modules. LithOS~\cite{lithos}, notably, re-implements runtime stacks with OS-like abstractions in user-space. Despite improved performance over purely generic algorithms, these approaches remain fundamentally restricted by embedding fixed, static policies directly within kernel modules or runtime stacks, requiring invasive kernel modifications for policy adjustments. This inherently restricts rapid experimentation, dynamic runtime adaptation, and safe deployment of new policies at runtime, limiting long-term policy flexibility and evolution.

\paragraph{Host User-Space Runtimes and Libraries}
Recent frameworks—such as Paella~\cite{paella}, Pie~\cite{pie}, XSched~\cite{xsched}, and KTransformers~\cite{ktransformers}—explicitly expose programmable interfaces at the user-space layer. Paella provides software-defined GPU scheduling for model serving, Pie enables developers to customize inference loops and KV-cache management via "inferlets," XSched introduces flexible, user-defined scheduling through its XQueue abstraction, and KTransformers supports programmable hybrid CPU-GPU inference scheduling and expert placement strategies.
However, these user-space systems share three fundamental limitations for GPU resource management. First, programmability remains inherently application-bound: policies are tightly coupled to specific runtimes, requiring invasive code modifications or porting existing applications onto specialized stacks, preventing broad reuse. Second, user-space runtimes lack global visibility and coordination across multiple tenants or frameworks. Confined to isolated process silos, they cannot safely share memory or bandwidth among multiple tenants, nor can they effectively mitigate interference caused by competing tenants or runtimes. Consequently, applications must conservatively pre-allocate resources (e.g., GPU memory) at startup to avoid runtime contention and faults, thus preventing dynamic resource sharing and significantly reducing utilization~\cite{lmcache}. Similarly, hardware-based partitioning techniques such as NVIDIA’s Multi-Instance GPU (MIG) impose fixed resource boundaries, which cannot dynamically adapt to bursty workloads or fluctuating demand. Third, user-space frameworks lack fine-grained, privileged interfaces to critical low-level mechanisms within the GPU driver, such as page fault handling, MMU updates, and interrupt delivery. As a result, policies remain limited to coarse-grained scheduling boundaries at kernel launches, precluding precise preemption strategies necessary for latency-sensitive tasks and rendering fine-grained compute-transfer overlaps impossible. Additionally, they cannot execute latency-critical policy logic directly within driver-level page fault handlers, nor enforce advanced scheduling conditions sensitive to warp-level or barrier-level progress states, or leverage GPU-side memory access patterns to inform sophisticated driver-level caching policies. Implementing such policies typically necessitates intrusive compiler modifications, thereby making the resulting policy implementations inherently non-transparent.

\paragraph{Binary Instrumentation and Profiling Tools on Device}
% \xiangyu{Three limitations for these tools:}
Tools such as NVBit~\cite{nvbit}, Neutrino~\cite{neutrino}, and GPU sanitizer frameworks inject logic directly into GPU binaries. NVBit performs dynamic SASS-level instrumentation, while Neutrino attaches programmable probes at the assembly layer to profile kernels at instruction granularity with an eBPF-like programming model. Despite their visibility, these tools have three limitations. First, they lack strong safety guarantees, as injected logic can crash or incur dead lock to hang applications. Second, they target offline profiling rather than online policy enforcement, operating in read-only modes that cannot regulate memory placement or thread scheduling. Third, they lack privileged host integration and therefore cannot coordinate policies beyond a single kernel; assembly-level instrumentation like Neutrino~\cite{neutrino} also restricts expressiveness and portability. Recent user-space approaches such as eGPU~\cite{egpu} extend eBPF to GPUs for observability, but remain limited to application-level instrumentation and incur prohibitive overheads (see \S\ref{sec:eval}).

\paragraph{Host-Based Kernel Programmability (CPU eBPF)}
CPU-side eBPF has been widely used to customize OS scheduling and resource management (e.g., \texttt{sched\_ext}, \texttt{cache\_ext}). However, extending this model to GPUs faces two fundamental barriers. First, host-based eBPF treats the GPU as an opaque peripheral: it can trace driver commands but cannot observe internal execution state (e.g., warp divergence), preventing reaction to on-chip bottlenecks. Second, unlike the Linux CPU scheduler refactored to support \texttt{sched\_ext}, monolithic GPU drivers expose no safe programmable extension points. Their resource management mechanisms are tightly coupled to low-level hardware interactions (e.g., MMU invalidation), and naïvely exposing such controls risks resource leaks, hardware hangs, or kernel panics—requiring carefully designed safe interfaces.

In summary, existing methods exhibit fundamental architectural asymmetry: host-side programmability lacks visibility into GPU-internal execution states and privileged interfaces, while device-side programmability is vendor-specific, opaque, and lacks safe host-side integration. This fundamental asymmetry severely limits the programmability, observability, and adaptability of GPU resource management across the system stack.

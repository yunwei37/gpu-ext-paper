\subsection{GPU Systems and Workload Diversity}
\label{sec:arch-gpu}

Modern GPU stacks consist of three layers:
User-space logic (applications and runtimes) includes frameworks (PyTorch, CUDA) and runtimes (e.g., vLLM~\cite{kwon2023efficient}, Salus~\cite{yu2020fine}, PILOT~\cite{ravi2021pilot}), which encode semantic information (e.g., neural network structures, latency constraints) and implement resource management policies (e.g., request scheduling, KV-cache offloading).
The OS kernel driver acts as the OS component, managing privileged hardware mechanisms such as the MMU, hardware interrupts, scheduling, and multi-tenant resource isolation. Under Unified Virtual Memory (UVM), which shares a virtual address space between host and device memory, applications may oversubscribe device memory, triggering driver-managed page faults and host-device migrations. Drivers typically employ fixed application-agnostic algorithms, such as LRU eviction.
Users submit GPU kernels to execute on the device; these kernels follow the SIMT (Single Instruction, Multiple Threads) execution model: on NVIDIA GPUs, GPU kernels execute in warps of 32 threads and are scheduled by GPU hardware at warp granularity. Internal GPU execution states, such as warp-level access patterns remain opaque to host-side drivers.

These resources require workload-specific management, yet static policies are ineffective. At the driver level, eviction and prefetch policy choice alone can swing execution time by up to 73\%~\cite{ganguly2019interplay,park2025helm}; LLM inference benefits from specialized KV-cache eviction rather than default LRU~\cite{sheng2023flexgen,kwon2023efficient}, GNN training requires aggressive sequential prefetch for irregular pointer-chasing accesses~\cite{lin2024towards,wang2016gunrock}, and vector search shifts between sequential index construction and random query phases~\cite{pan2024survey,cao2023gpu}, yet each strategy may degrade other workloads. Even within single deployments, optimal scheduling priority and preemption policies vary over time as multi-tenant demands fluctuate\cite{fan2025gpreempt,wang2024gcaps}. \Cref{fig:access_patterns} illustrates this diversity: we trace page-fault addresses over time on an RTX 5090 with 1.5$\times$ GPU memory oversubscription under UVM. LLM MoE inference shows periodic stride bursts from expert activations; GNN training exhibits irregular random access from pointer-chasing graph traversal; vector search alternates between sequential scans (index build) and random probes (query). These patterns demand fundamentally different prefetch and eviction strategies, yet the driver applies one fixed policy to all. On the device side, \Cref{fig:thread_scheduling} shows a 127$\times$ SM load imbalance in a vector-add GPU kernel, invisible to host-side drivers.

\subsection{Agent-Based Policy Exploration}
\label{sec:motivation-agent}

Automated OS policy exploration assisted by AI agents is well-suited to the large GPU policy space, yet requires a safe and programmable interface that current GPU stacks do not provide. Unlike traditional parameter-tuning methods, AI agents~\cite{dwivedula2025policysmith,zheng2025schedcp} directly generate policy logic, evaluate performance, and refine based on feedback, exploring richer strategies tailored to specific workloads. However, without a safe OS interface, agent-generated policies risk OS kernel panics or GPU hangs from buggy code; with only user-space APIs, agents cannot explore driver-level decisions such as eviction ordering or fault-path prefetching.

To enable effective agent-driven GPU policy optimization and benefit human developers, we require an OS interface with three key properties: dynamic and transparent policy loading, so agents can rapidly deploy and iterate policies at runtime without restarting applications or rebuilding OS kernel modules; programmable policy logic, to express flexible heuristics beyond fixed configuration knobs; and safety and isolation, to robustly handle automatically generated candidate policies without OS kernel panics or corrupting GPU device states. %No existing GPU resource management interface simultaneously meets these goals, motivating the need for a new OS abstraction tailored specifically to GPU extensions.

\subsection{Limitations of Existing Approaches}
\label{sec:motivation-limitations}

Existing approaches impose a tradeoff between programmability and control, failing to provide a dynamic, programmable, and safe OS interface for GPU resource management.

\paragraph{Driver-Level Policies.}
Driver-level approaches either expose fixed knobs (e.g., \texttt{cudaMemAdvise}, driver module parameters) that select among preset behaviors, or embed custom logic directly into driver code. Systems like TimeGraph~\cite{kato2011timegraph}, Gdev~\cite{kato2012gdev}, and OS kernel interception methods~\cite{kernelintercept} embed scheduling and memory-management logic into driver modules. More recent work such as GPREEMPT~\cite{fan2025gpreempt} and GCAPS~\cite{wang2024gcaps} adds priority-based preemption, and LithOS~\cite{coppock2025lithos} re-implements runtime stacks with OS-like abstractions. Despite improved performance, all these approaches require OS kernel or driver modifications to change policy, making them neither safely iterable nor rapidly deployable.

\paragraph{Host User-Space Runtimes and Libraries.}
User-space frameworks~\cite{ng2023paella,gim2025pie,shen2025xsched,chen2025ktransformers,coppock2025lithos} offer programmability but face three limitations. First, policies are application-bound, requiring per-framework implementation and preventing reuse across ecosystems. Second, process-level isolation prevents cross-tenant visibility and coordinated memory-scheduling decisions across tenants~\cite{xiao2018gandiva,yu2020fine}; hardware partitioning such as MIG imposes fixed resource boundaries that cannot be dynamically rebalanced. Third, user-space code cannot access privileged driver mechanisms, leaving policies constrained to GPU kernel launch boundaries and unable to execute on latency-critical paths (e.g., page-fault handlers), perform precise preemption, or exploit GPU-side warp-level access patterns.

\subsection{GPU-Specific Challenges for eBPF Extensibility}
\label{sec:motivation-challenges}

eBPF (extended Berkeley Packet Filter) allows user-supplied programs to run safely inside the OS kernel. Programs are statically verified at load time for termination, memory safety, and type correctness, then JIT-compiled to native code. The verifier guarantees that programs call only approved helpers and kfuncs (OS kernel functions). eBPF programs are callbacks attached to hook points such as \texttt{struct_ops}, \texttt{kprobe}, and \texttt{uprobe}. This enables runtime-programmable OS extensions, including \texttt{sched_ext}~\cite{schedext-docs} for CPU scheduling, \texttt{cache_ext}~\cite{zussman2025cache_ext} for page cache eviction, and XDP for network packet processing. In these systems, each BPF callback makes a single synchronous decision at a fixed transition point, with effects immediately taking place on local CPU resources, and each subsystem is extended independently.

However, the CPU eBPF model does not directly transfer to GPUs. Three mismatches between the CPU model and GPU architecture create challenges beyond the lack of safe programmable extension in GPU drivers.

First, cross-device latency: CPU eBPF callbacks execute synchronously, but GPU operations such as page migration cross the PCIe boundary and take milliseconds (\S\ref{sec:arch-gpu}). Policies must initiate transitions asynchronously and act proactively, not only reactively at the fault.

Second, memory-scheduling coupling: CPU extensibility treats scheduling and memory as independent subsystems (\texttt{sched\_ext} and \texttt{cache\_ext}), but on GPU, limited device memory tightly couples these domains, as a page fault is simultaneously a memory event and a scheduling stall. GPU policies must coordinate across both.

Third, fragmented visibility: CPU eBPF runs on the same processor it manages, but in GPU stacks, policy-relevant state is split across layers. Downward, GPU-internal execution state such as per-warp access patterns and SM utilization remains opaque to the host (\S\ref{sec:arch-gpu}). Upward, GPU runtimes bypass the OS kernel for work submission (e.g., user-space command buffers and doorbells), so the driver sees only coarse lifecycle events, not individual GPU kernel launches or application phase transitions (e.g., LLM prefill-to-decode, FAISS build-to-search).
Naively exposing low-level GPU driver controls without addressing these mismatches risks resource leaks, hardware hangs, or OS kernel panics.

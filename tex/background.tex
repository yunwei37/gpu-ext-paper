\section{Background and Motivation}

\subsection{GPU-Centric Workloads and Systems}

GPUs have become indispensable in modern datacenters, supporting an increasingly diverse and demanding set of workloads---from large-scale deep learning training and latency-sensitive inference to irregular computations like graph analytics and graphics rendering. The importance of GPUs spans ML, analytics, and HPC applications, where they work in concert with CPUs and high-speed interconnects (PCIe, NVLink) to deliver high throughput and low latency.

\subsection{Limitations of Existing GPU Policies}

\paragraph{UVM Memory Management}
Unified Virtual Memory (UVM) greatly simplifies programming by abstracting memory management across CPUs and GPUs. However, current UVM implementations rely on fixed heuristics that cannot adapt policies for prefetching, thrashing mitigation, or eviction based on workload characteristics. These rigid policies lead to suboptimal performance, especially for memory-intensive workloads with diverse access patterns.

\paragraph{GPU Kernel Scheduling}
Existing GPU admission and resource allocation policies remain rigid and coarse-grained, using fixed timeslices and inflexible GPU admission and isolation policies. These limitations prevent fine-grained control over kernel scheduling, making it difficult to prioritize latency-sensitive workloads or dynamically adjust resource allocation in multi-tenant environments.

\paragraph{Observability}
Current GPU observability tools like CUPTI~\cite{cupti} and NVBit~\cite{villa2019nvbit} provide detailed monitoring data but often have high overhead. More critically, they provide data without actionable control---developers can observe what is happening but cannot dynamically inject custom instrumentation or adapt policies based on runtime observations. As shown in \Cref{fig:latency}, current tools cannot inject logic into running kernels without halting execution.

\subsection{Programmability Policy Runtimes}

The broader systems community has demonstrated significant benefits from externalizing and customizing OS policies through frameworks like extended Berkeley Packet Filter (eBPF). Examples such as sched\_ext for Linux scheduling, cache\_ext for page-cache eviction, and struct\_ops for TCP congestion control have illustrated substantial performance and adaptability gains when policies can be dynamically loaded, safely verified, and executed directly within kernel contexts. The eBPF ecosystem, originally a kernel packet filter, now provides unified infrastructure for observability, security, and networking.

However, while these successes illustrate the potential of policy programmability on CPUs, directly extending these ideas to GPU systems poses significant new challenges. CPU-side programmability alone is insufficient, as critical GPU management decisions are fundamentally embedded in GPU device execution contexts inaccessible from the CPU host. Conversely, GPU-side programmability alone is not enough either, as isolated GPU-only policies lack visibility into broader system state and coordination essential for coherent end-to-end policy decisions. This clear contrast demonstrates why CPU-side programmability alone doesn't solve GPU policy problems---a unified approach spanning both CPU and GPU contexts is essential.

\subsection{Systemic Challenges in GPU Programmability}

\paragraph{Decoupling Mechanisms from Policies}
Modern GPU stacks suffer from tight coupling between resource management mechanisms (e.g., Unified Virtual Memory page migration, kernel execution lifecycle management, performance event collection) and embedded, hard-coded policy logic within kernel modules, closed-source vendor libraries or GPU device code. This tight coupling severely restricts the ability to adapt policies to diverse and evolving workloads, inhibits rapid experimentation, and fundamentally limits the adaptability of GPU infrastructure in production datacenters.

\paragraph{Unified Cross-Layer Coordination}
GPU-centric workloads increasingly demand adaptive, fine-grained resource management decisions that span both host-side (CPU) and device-side (GPU) execution contexts. Current GPU stacks suffer from a fundamental fragmentation: host-side policies (e.g., UVM memory management, scheduling) lack visibility into GPU-internal runtime states, while device-side policy (e.g., memory sync, thread block management, trace instrumentation) are opaque, vendor-specific, and largely inaccessible to host-side management logic. This fundamental asymmetry in policy expression and execution severely constrains the programmability, observability, and adaptability of GPU datacenter resource management.

\paragraph{Safety in Critical Paths}
Allowing programmable policies to execute within critical GPU kernel paths and Linux kernel drivers poses significant risks: faulty or unsafe policy logic can cause GPU hangs or kernel panics, potentially leading to cluster-wide failures, or incur unacceptable latency overhead on performance-sensitive paths such as GPU scheduling or memory fault handling. Existing solutions like nvbit or user-space policy framework either impose substantial performance overhead, making them impractical for latency-critical GPU datacenter workloads, or provide insufficient isolation to contain faults effectively.

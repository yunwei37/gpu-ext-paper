\subsection{GPU Systems and Workload Diversity}
\label{sec:arch-gpu}

This paper focuses on three domains of GPU resource management that span the software stack: memory placement and migration, compute scheduling, and on-device thread scheduling.
User-space frameworks and applications (e.g., vLLM~\cite{kwon2023efficient}, Salus~\cite{yu2020fine}, PILOT~\cite{ravi2021pilot}) encode semantic information (e.g., neural network structures, latency constraints) and implement policies like request scheduling and KV-cache offloading.
The OS kernel driver manages memory placement, compute scheduling, and multi-tenant resource isolation through privileged hardware mechanisms (MMU, interrupts). Under Unified Virtual Memory (UVM), which shares a virtual address space between host and device memory, applications may oversubscribe device memory, triggering driver-managed page faults and host-device migrations. Drivers typically employ fixed application-agnostic algorithms, such as LRU eviction.
The GPU device executes kernels in the SIMT (Single Instruction, Multiple Threads) model: on NVIDIA GPUs, warps of 32 threads execute the same instruction in lockstep, and firmware schedules them on Streaming Multiprocessors (SMs). Internal execution states such as warp access patterns remain opaque to host-side drivers.

\subsection{Agent-Based Policy Exploration}
\label{sec:motivation-agent}

Automated OS policy exploration assisted by AI agents is well-suited to the large GPU policy space, yet requires a safe and programmable interface that current GPU stacks do not provide. Unlike traditional parameter-tuning methods, AI agents~\cite{dwivedula2025policysmith,zheng2025schedcp} directly generate policy logic, evaluate performance, and refine based on feedback, exploring richer strategies tailored to specific workloads. However, without a safe OS interface, agent-generated policies risk OS kernel panics or GPU hangs from buggy code; with only user-space APIs, agents cannot explore driver-level decisions such as eviction ordering or fault-path prefetching.

To enable effective agent-driven GPU policy optimization and benefit human developers, we require an OS interface with three key properties: dynamic and transparent policy loading, so agents can rapidly deploy and iterate policies at runtime without restarting applications or rebuilding OS kernel modules; programmable policy logic, to express flexible heuristics beyond fixed configuration knobs; and safety and isolation, to robustly handle automatically generated candidate policies without OS kernel panics or corrupting GPU device states.

\subsection{Limitations of Existing Approaches}
\label{sec:motivation-limitations}

Existing approaches impose a tradeoff between programmability and control, failing to provide a dynamic, programmable, and safe OS interface for GPU resource management.

\paragraph{Driver-Level Policies.}
Driver-level approaches either expose fixed knobs (e.g., \texttt{cudaMemAdvise}, driver module parameters) that select among preset behaviors, or embed custom logic directly into driver code. Systems like TimeGraph~\cite{kato2011timegraph}, Gdev~\cite{kato2012gdev}, and OS kernel interception methods~\cite{kernelintercept} embed scheduling and memory-management logic into driver modules. More recent work such as GPREEMPT~\cite{fan2025gpreempt} and GCAPS~\cite{wang2024gcaps} adds priority-based preemption, and LithOS~\cite{coppock2025lithos} re-implements runtime stacks with OS-like abstractions. Despite improved performance, all these approaches require OS kernel or driver modifications to change policy, making them neither safely iterable nor rapidly deployable.

\paragraph{Host User-Space Runtimes and Libraries.}
User-space frameworks~\cite{ng2023paella,gim2025pie,shen2025xsched,chen2025ktransformers,coppock2025lithos} offer programmability but face three limitations. First, policies are application-bound, requiring per-framework implementation and preventing reuse across ecosystems. Second, process-level isolation prevents cross-tenant visibility and coordinated memory-scheduling decisions across tenants~\cite{xiao2018gandiva,yu2020fine}; hardware partitioning such as MIG imposes fixed resource boundaries that cannot be dynamically rebalanced. Third, user-space code cannot access privileged driver mechanisms, leaving policies constrained to GPU kernel launch boundaries and unable to execute on latency-critical paths (e.g., page-fault handlers), perform precise preemption, or exploit GPU-side warp-level access patterns.

\subsection{GPU Systems Architecture}
\label{sec:arch-gpu}

Modern GPU stacks consist of three layers:
\textbf{User-space logic (applications and runtimes)} includes frameworks (PyTorch, CUDA) and runtimes (e.g., vLLM~\cite{kwon2023efficient}, Salus~\cite{yu2020fine}, PILOT~\cite{ravi2021pilot}), which encode semantic information (e.g., neural network structures, latency constraints) and implement resource management policies (e.g., request scheduling, KV-cache offloading).
\textbf{The kernel driver} acts as the OS component, managing privileged hardware mechanisms such as the MMU, hardware interrupts, scheduling, and multi-tenant resource isolation. Under Unified Virtual Memory (UVM), which shares a virtual address space between host and device memory, applications may oversubscribe device memory, triggering driver-managed page faults and host-device migrations. Drivers typically employ fixed application-agnostic algorithms, such as LRU eviction.
Users submit \textbf{GPU kernels} to execute on the device; these kernels follow the SIMT (Single Instruction, Multiple Threads) execution model: on NVIDIA GPUs, GPU kernels execute in warps of 32 threads and are scheduled by GPU hardware at warp granularity. Internal GPU execution states, such as warp-level access patterns remain opaque to host-side drivers.

eBPF (extended Berkeley Packet Filter) allows user-supplied programs to run safely inside the OS kernel. Programs are statically verified at load time for termination, memory safety, and type correctness, then JIT-compiled to native code. The verifier guarantees that programs access only permitted memory regions and call only approved helpers and kfuncs (kernel functions used by eBPF). Programs attach to kernel-defined hook points via mechanisms such as \texttt{struct\_ops}, where the kernel invokes BPF callbacks at specific decision points and falls back to default behavior if no program is loaded. This enables runtime-programmable extensions to kernel subsystems: \texttt{sched\_ext}~\cite{schedext-docs} makes CPU scheduling programmable and \texttt{cache\_ext}~\cite{zussman2025cache_ext} extends page cache eviction via \texttt{struct\_ops}; XDP attaches eBPF programs at the network driver level to process packets. In these systems, each BPF callback makes a single synchronous decision at one transition point, with effects taking place immediately on local CPU resources, and each subsystem (scheduling, memory, networking) is extended independently.

\subsection{Agent-Based Policy Exploration}
\label{sec:motivation-agent}

Automated OS policy exploration assisted by AI agents is well-suited to the large GPU policy space, yet requires a safe and programmable interface that current GPU stacks do not provide. Unlike traditional parameter-tuning methods, AI agents~\cite{dwivedula2025policysmith,zheng2025schedcp} directly generate policy logic, evaluate performance, and refine based on feedback, exploring richer strategies tailored to specific workloads. However, without a safe OS interface, agent-generated policies risk kernel panics or GPU hangs from buggy code; with only user-space APIs, agents cannot explore driver-level decisions such as eviction ordering or fault-path prefetching.

To enable effective agent-driven GPU policy optimization and benefit human developers, we require an OS interface with three key properties: \textbf{dynamic and transparent policy loading}, so agents can rapidly deploy and iterate policies at runtime without restarting applications or rebuilding kernel modules; \textbf{programmable policy logic}, to express flexible heuristics beyond fixed configuration knobs; and \textbf{safety and isolation}, to robustly handle automatically generated candidate policies without crashing kernels or corrupting GPU device states. %No existing GPU resource management interface simultaneously meets these goals, motivating the need for a new OS abstraction tailored specifically to GPU extensions.

\subsection{Limitations of Existing Approaches}
\label{sec:motivation-limitations}

Existing approaches impose a tradeoff between programmability and control, failing to provide a dynamic, programmable, and safe OS interface for GPU resource management.

\paragraph{Driver-Level Policies.}
Driver-level approaches either expose fixed knobs (e.g., \texttt{cudaMemAdvise}, driver module parameters) that select among preset behaviors, or embed custom logic directly into driver code. Systems like TimeGraph~\cite{kato2011timegraph}, Gdev~\cite{kato2012gdev}, and kernel interception methods~\cite{kernelintercept} embed scheduling and memory-management logic into driver modules. More recent work such as GPREEMPT~\cite{fan2025gpreempt} and GCAPS~\cite{wang2024gcaps} adds priority-based preemption, and LithOS~\cite{coppock2025lithos} re-implements runtime stacks with OS-like abstractions. Despite improved performance, all these approaches require kernel or driver modifications to change policy, making them neither safely iterable nor rapidly deployable.

\paragraph{Host User-Space Runtimes and Libraries.}
User-space frameworks~\cite{ng2023paella,gim2025pie,shen2025xsched,chen2025ktransformers,coppock2025lithos} offer programmability but face three limitations. First, policies are application-bound, requiring per-framework implementation and preventing reuse across ecosystems. Second, process-level isolation prevents cross-tenant visibility and coordinated memory-scheduling decisions across tenants~\cite{xiao2018gandiva,yu2020fine}; hardware partitioning such as MIG imposes fixed resource boundaries that cannot be dynamically rebalanced. Third, user-space code cannot access privileged driver mechanisms, leaving policies constrained to GPU kernel launch boundaries and unable to execute on latency-critical paths (e.g., page-fault handlers), perform precise preemption, or exploit GPU-side warp-level access patterns.

\subsection{GPU-Specific Challenges for eBPF Extensibility}
\label{sec:motivation-challenges}
% In CPU extensibility, a policy's natural trigger point is also its optimal decision point: when a packet arrives, the right time to filter it is now; when a process becomes runnable, the right time to schedule it is now. GPU breaks this: when a page fault arrives, the optimal action—prefetch—should have begun milliseconds earlier, at an event visible only in user-space (kernel launch). The decision point and the trigger point are separated not just across layers, but across time.

eBPF provides safe runtime extensibility for CPU scheduling~\cite{schedext-docs} and page caching~\cite{zussman2025cache_ext}, but the CPU eBPF model (\S\ref{sec:background}) does not directly transfer to GPUs. Three mismatches between the CPU model and GPU architecture create challenges beyond the lack of safe programmable extension in GPU drivers.
First, \emph{cross-device latency}: CPU eBPF callbacks execute synchronously, but GPU operations such as page migration cross the PCIe boundary and take milliseconds (\S\ref{sec:arch-gpu}). Policies must initiate transitions asynchronously and act proactively, not only reactively at the fault.
Second, \emph{memory-scheduling coupling}: CPU extensibility treats scheduling and memory as independent subsystems (\texttt{sched\_ext} and \texttt{cache\_ext}), but on GPU, limited device memory tightly couples these domains, as a page fault is simultaneously a memory event and a scheduling stall. GPU policies must coordinate across both.
Third, \emph{fragmented visibility}: CPU eBPF runs on the same processor it manages, but in GPU stacks, policy-relevant state is split across layers. Downward, GPU-internal execution state such as per-warp access patterns and SM utilization remains opaque to the host (\S\ref{sec:arch-gpu}). Upward, GPU runtimes bypass the kernel for work submission (e.g., user-space command buffers and doorbells), so the driver sees only coarse lifecycle events, not individual kernel launches or application phase transitions (e.g., LLM prefill-to-decode, FAISS build-to-search).
Naively exposing low-level GPU driver controls without addressing these mismatches risks resource leaks, hardware hangs, or kernel panics.

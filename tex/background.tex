\subsection{GPU Systems and Workload Diversity}
\label{sec:arch-gpu}

\arq{I think this is too many ideas for one paragraph  It should probably reference Figure 1 (!)}
This paper focuses on three domains of GPU resource management that span the software stack: memory placement and migration, compute scheduling, and on-device thread scheduling.
User-space frameworks and applications (e.g., vLLM~\cite{kwon2023efficient}, Salus~\cite{yu2020fine}, PILOT~\cite{ravi2021pilot}) encode semantic information (e.g., neural network structures, latency constraints) and implement policies like request scheduling and KV-cache offloading.
The OS kernel driver manages memory placement, compute scheduling, and multi-tenant resource isolation through privileged hardware mechanisms (MMU, interrupts). Under Unified Virtual Memory (UVM), which shares a virtual address space between host and device memory, applications may oversubscribe device memory, triggering driver-managed page faults and host-device migrations. Drivers typically employ fixed application-agnostic algorithms, such as LRU eviction.
The GPU device executes GPU kernels in the SIMT (Single Instruction, Multiple Threads) model: on NVIDIA GPUs, warps of 32 threads execute the same instruction in lockstep, and firmware schedules them on Streaming Multiprocessors (SMs). Internal execution states such as warp access patterns remain opaque to host-side drivers.

These resources require workload-specific management. UVM eviction and prefetch policy choice alone can change execution time by up to 73\%~\cite{ganguly2019interplay,park2025helm}. For compute scheduling, even within single deployments, optimal priority and preemption policies vary over time as multi-tenant demands fluctuate~\cite{fan2025gpreempt,wang2024gcaps}. \sys{}'s eBPF-based tracing tools (\S\ref{sec:eval}) results confirm this diversity: \Cref{fig:access_patterns} captures memory page-fault addresses over time under UVM, showing that LLM MoE inference exhibits periodic stride bursts from expert activations, benefiting from specialized eviction rather than default LRU~\cite{sheng2023flexgen,kwon2023efficient}; GNN training shows irregular random access from pointer-chasing graph traversal, requiring aggressive sequential prefetch~\cite{lin2024towards,wang2016gunrock}; and vector search alternates between sequential scans (index build) and random probes (query)~\cite{pan2024survey,cao2023gpu}, yet each strategy may degrade other workloads. \Cref{fig:thread_scheduling} reveals a 127$\times$ SM scheduling load imbalance in a vector-add GPU kernel, invisible to host-side drivers and amenable to custom thread scheduling. These patterns demand different strategies across all three domains, yet current drivers and firmware apply one fixed policy to all.

\subsection{Agent-Based Policy Exploration}
\label{sec:motivation-agent}

Automated OS policy exploration assisted by AI agents is well-suited to the large GPU policy space, yet requires a programmable interface that current GPU stacks do not provide. Unlike traditional parameter-tuning methods, AI agents~\cite{dwivedula2025policysmith,zheng2025schedcp} directly generate policy logic, evaluate performance, and refine based on feedback, exploring richer strategies tailored to specific workloads. However, existing GPU stacks expose only fixed configuration knobs (e.g., \texttt{cudaMemAdvise}, driver module parameters), not programmable policy interfaces, preventing agents from expressing complex heuristics such as workload-aware eviction ordering or adaptive prefetch strategies.

To enable effective agent-driven GPU policy optimization and benefit human developers, we require an OS interface with three key properties: safe, dynamic, and full-stack: safe, to robustly handle automatically generated candidate policies without OS kernel panics or corrupting GPU device states; dynamic, so agents can rapidly deploy and iterate policies at runtime without restarting applications or rebuilding OS kernel modules. To be effective, it requires full-stack: policies need to observe GPU-internal execution state, coordinate across tenants, and control driver-level decisions such as eviction ordering and fault-path prefetching.

\subsection{Limitations of Existing Approaches}
\label{sec:motivation-limitations}

\arq{Make sure to critique these existing approaches by saying they are not safe, dynamic, or full-stack.}
Existing approaches fail to simultaneously provide a safe, dynamic, and full-stack programmable OS interface for GPU resource management.

\paragraph{Driver-Level Policies.}
Driver-level approaches either expose fixed knobs (e.g., \texttt{cudaMemAdvise}, driver module parameters) that select among preset behaviors, or embed custom logic directly into driver code. Systems like TimeGraph~\cite{kato2011timegraph}, Gdev~\cite{kato2012gdev}, and OS kernel interception methods~\cite{kernelintercept} embed scheduling and memory-management logic into driver modules. More recent work such as GPREEMPT~\cite{fan2025gpreempt} and GCAPS~\cite{wang2024gcaps} adds priority-based preemption, and LithOS~\cite{coppock2025lithos} re-implements runtime stacks with OS-like abstractions. Despite improved performance, all these approaches require OS kernel or driver modifications to change policy, making them neither safely iterable nor rapidly deployable.

\paragraph{Host User-Space Runtimes and Libraries.}
User-space frameworks~\cite{ng2023paella,gim2025pie,shen2025xsched,chen2025ktransformers,coppock2025lithos} offer programmability but face three limitations. First, policies are application-bound, requiring per-framework implementation and preventing reuse across ecosystems. Second, process-level isolation prevents cross-tenant visibility and coordinated memory-scheduling decisions across tenants~\cite{xiao2018gandiva,yu2020fine}; hardware partitioning such as MIG imposes fixed resource boundaries that cannot be dynamically rebalanced. Third, user-space code cannot access privileged driver mechanisms, leaving policies constrained to GPU kernel launch boundaries and unable to execute on latency-critical paths (e.g., page-fault handlers), perform precise preemption, or exploit GPU-side warp-level access patterns.

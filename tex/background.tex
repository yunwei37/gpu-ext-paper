\section{Background and Motivation}

\subsection{The Diversity of GPU-Centric Workloads}
% \xiangyu{Workloads in CPU clusters}

Modern GPU-centric systems host heterogeneous workloads with fundamentally conflicting resource requirements. Generative AI inference pipelines are increasingly complex: Prefill-Decode disaggregation separates compute-intensive prompt processing from bandwidth-bound token generation across devices~\cite{zhong2024distserve,patel2024splitwise}; KV-cache offloading alternates between transfer-intensive and memory-bound phases~\cite{sheng2023flexgen,kwon2023efficient}; Mixture-of-Experts (MoE) models generate sparse activations necessitating frequent paging of expert weights~\cite{gale2023megablocks,he2021fastmoe}. Neural network training is equally diverse: dense training relies on predictable synchronization, whereas Graph Neural Network (GNN) training and sparse embedding lookups exhibit irregular pointer-chasing accesses that defy hardware prefetching. Vector search workloads further add variability: HNSW indexing demands random access, while IVF indexing emphasizes high-throughput sequential scanning. \Cref{fig:access_patterns} visually highlights such distinct memory access behaviors through page fault tracing, underscoring that static memory management policies cannot optimally serve all workloads. Similarly, GPU thread scheduling also shows substantial variability and imbalance (\Cref{fig:thread_scheduling}), with uneven load distribution across SMs and warps. This unpredictable scheduling behavior, invisible to conventional profiling tools, motivates fine-grained, programmable GPU observability.

\paragraph{User-Space Logic (Applications \& Runtimes)}
% userspace include 2 parts: runtime and application. discuss them separately.
High-level frameworks (e.g., PyTorch) and runtimes (e.g., CUDA libraries) operate entirely in user space, managing operation graphs, tensor layouts, and command submissions via memory-mapped interfaces or ioctl calls to drivers. These user-space components encode rich semantic information, such as neural network structures and latency constraints. Runtime systems like vLLM~\cite{kwon2023efficient}, fine-grained sharing frameworks such as Salus~\cite{salus}, and UVM-focused runtimes like PILOT~\cite{pilot} also implement sophisticated resource management policies in application-specific user-space logic.

\paragraph{The One-size-fits-all Kernel Driver}
The GPU driver acts as the OS component for GPU systems, managing privileged low-level hardware mechanisms including the Memory Management Unit (MMU), hardware interrupts, and kernel scheduling. Typical drivers are monolithic, implementing generic, application-agnostic resource-management algorithms such as Least Recently Used (LRU)-based page eviction, simple round-robin scheduling for context switching, and basic tree-based prefetching mechanisms in Unified Virtual Memory scenarios. These drivers traditionally offer coarse-grained policies, intentionally abstracting away application-specific semantics.

\paragraph{Device-Side Execution}

The GPU device executes computations via user-defined device kernels and proprietary vendor firmware, which are compiled into static binaries specifying precise thread-level SIMT behaviors. GPU hardware schedulers manage thread execution at warp granularity. Device kernels and firmware lack runtime adaptability, making critical internal states—such as warp divergence, cache thrashing, and thread-level execution bottlenecks—completely opaque to host-side drivers. This architectural opacity severely constrains host-driven, runtime workload-adaptive optimization opportunities.

In summary, modern GPU software stacks are characterized by a tight coupling between resource-management mechanisms (memory migration, kernel scheduling, and event tracing) and rigid, statically-defined policy logic embedded within kernel drivers, closed-source firmware, and statically-compiled device kernels. This architectural coupling significantly limits runtime policy flexibility, programmability, and adaptability in modern GPU-centric infrastructures.

\subsection{Limitations of Existing Extensibility Mechanisms}

Existing approaches attempting to mitigate the rigidity described above fall broadly into four categories, each facing fundamental limitations:

\paragraph{Driver-Level Kernel-Space Policies.}

Recent research has introduced driver-level resource control by moving policy decisions into kernel drivers or intercepting driver-level events. Systems like TimeGraph~\cite{kato2011timegraph}, Gdev~\cite{kato2012gdev}, GPREEMPT~\cite{fan2025gpreempt}, LithOS~\cite{lithos}, GCAPS~\cite{wang2024gcaps}, and kernel interception methods~\cite{kernelintercept} embed customized scheduling and memory-management logic into kernel-space or user-space driver modules. LithOS~\cite{lithos}, notably, re-implements runtime stacks with OS-like abstractions in user-space. Despite improved performance over purely generic algorithms, these approaches remain fundamentally restricted by embedding fixed, static policies directly within kernel modules or runtime stacks, requiring invasive kernel modifications for policy adjustments. This inherently restricts rapid experimentation, dynamic runtime adaptation, and safe deployment of new policies at runtime, limiting long-term policy flexibility and evolution.

\paragraph{Host User-Space Runtimes and Libraries}
Recent frameworks—such as Paella~\cite{ng2023paella}, Pie~\cite{pie}, XSched~\cite{xsched}, and KTransformers~\cite{ktransformers}—expose explicit programmability at the user-space layer. Paella provides software-defined GPU scheduling for model serving; Pie enables developers to customize inference loops and KV-cache management via “inferlets”; XSched supports flexible, user-defined scheduling through its XQueue abstraction; and KTransformers exposes programmable hybrid CPU–GPU scheduling and expert-placement strategies. Despite this programmability, user-space systems share three fundamental limitations.
First, programmability remains inherently application-bound: policies must be written against a specific framework or runtime, requiring invasive code changes or porting applications onto specialized stacks, which prevents broad reuse.
Second, user-space runtimes lack global visibility and coordination across multi-tenant, multi-framework environments. Confined to isolated process silos, they cannot safely share memory or bandwidth or mitigate interference from co-located tenants. As a result, applications conservatively pre-allocate resources (e.g., GPU memory) at startup to avoid contention and faults~\cite{lmcache}, suppressing dynamic sharing and significantly reducing utilization. Likewise, hardware-based partitioning techniques such as NVIDIA’s Multi-Instance GPU (MIG) impose fixed resource boundaries that user-space runtimes cannot adapt or rebalance in response to bursty workload demands.
Third, user-space frameworks lack privileged access to low-level driver mechanisms—such as page-fault handling, MMU updates, and interrupt delivery—leaving policies constrained to coarse-grained kernel-launch boundaries. This precludes precise preemption needed for latency-sensitive tasks and prevents fine-grained compute–transfer overlap. Moreover, they cannot execute policy logic on latency-critical paths (e.g., page-fault handlers), nor exploit GPU-side warp-level or barrier-level access patterns to guide driver-level caching decisions.

\paragraph{Binary Instrumentation and Profiling Tools on Device}
% \xiangyu{Three limitations for these tools:}
Tools such as NVBit~\cite{nvbit}, Neutrino~\cite{neutrino}, and GPU sanitizer frameworks inject logic directly into GPU binaries. NVBit supports dynamic SASS-level instrumentation, while Neutrino provides instruction-level profiling via programmable assembly-layer probes with an eBPF-like interface. Despite high kernel visibility, these tools face three major limitations. First, they lack strong safety guarantees, as injected logic can cause crashes or application hangs with dead locks. Second, they primarily target offline profiling rather than online policy enforcement, operating in read-only modes that cannot actively control memory placement or thread scheduling. Third, lacking privileged host-side integration, they are unable to coordinate policies across multiple processes. Additionally, assembly-level instrumentation inherently restricts expressiveness and portability~\cite{neutrino}. Recent approaches like eGPU~\cite{egpu} extend eBPF to GPU instrumentation but remain limited to user-space observability with prohibitive runtime overheads (see \S\ref{sec:eval}).

\paragraph{Host-Based Kernel Programmability (CPU eBPF)}
CPU-side eBPF has been widely used to customize OS scheduling and resource management (e.g., \texttt{sched\_ext}, \texttt{cache\_ext}). However, extending this model to GPUs faces two fundamental barriers. First, host-based eBPF treats the GPU as an opaque peripheral: it can trace driver commands but cannot observe internal execution state (e.g., warp divergence), preventing reaction to on-chip bottlenecks. Second, unlike the Linux CPU scheduler refactored to support \texttt{sched\_ext}, monolithic GPU drivers expose no safe programmable extension points. Their resource management mechanisms are tightly coupled to low-level hardware interactions (e.g., MMU invalidation), and naïvely exposing such controls risks resource leaks, hardware hangs, or kernel panics—requiring carefully designed safe interfaces. In summary, existing methods exhibit architectural asymmetry: host-side programmability lacks visibility into GPU-internal states, while device-side approaches are vendor-specific, opaque, and lack safe host integration, fundamentally limiting GPU resource management flexibility.

\section{Background}

\subsection{GPU Systems Architecture}
\label{sec:arch-gpu}

Modern GPU stacks consist of three layers:
\textbf{User-space logic (applications and runtimes)} includes frameworks (PyTorch, CUDA) and runtimes (e.g., vLLM~\cite{kwon2023efficient}, Salus~\cite{yu2020fine}, PILOT~\cite{ravi2021pilot}), which encode rich semantic information (e.g., neural network structures, latency constraints) and implement resource management policies (e.g., request scheduling, KV-cache offloading).
\textbf{The kernel driver} acts as the OS component, managing privileged hardware mechanisms such as the MMU, hardware interrupts, scheduling, and multi-tenant resource isolation. Under Unified Virtual Memory (UVM), which shares a single virtual address space between host and device memory, applications may oversubscribe limited device memory capacity, triggering driver-managed page faults and host-device data migrations. Drivers typically employ fixed application-agnostic algorithms, such as LRU eviction.
Users submit \textbf{GPU kernels} to execute on the device; these kernels follow the SIMT (Single Instruction, Multiple Threads) execution model and are scheduled by GPU hardware at warp granularity. Internal GPU execution states, including warp-level access patterns and Streaming Multiprocessor (SM) utilization, remain opaque to host-side drivers.

\subsection{eBPF and OS Kernel Extensibility}
\label{sec:background}

% Moved from "Limitations" — CPU eBPF paragraph, reframed as background on eBPF
eBPF (extended Berkeley Packet Filter) allows user-supplied programs to run safely inside the OS kernel. Programs are statically verified at load time for termination, memory safety, and type correctness, then JIT-compiled to native code. The verifier guarantees that programs access only permitted memory regions and call only approved helpers and kfuncs(kernel functions used by eBPF). Programs attach to kernel-defined hook points via mechanisms such as \texttt{struct\_ops}, where the kernel invokes BPF callbacks at specific decision points and falls back to default behavior if no program is loaded. This mechanism has enabled runtime-programmable extensions to kernel subsystems: \texttt{sched\_ext}~\cite{schedext-docs} makes CPU scheduling programmable and \texttt{cache\_ext}~\cite{zussman2025cache_ext} extends page cache eviction via \texttt{struct\_ops}; XDP attaches eBPF programs at the network driver level to process packets. In these systems, each BPF callback makes a single synchronous decision at one transition point, with effects taking place immediately on local CPU resources, and each subsystem (scheduling, memory, networking) is extended independently.

\section{Motivation}

\subsection{The Diversity of GPU-Centric Workloads}

% \arq{We want to show that we need/want deployment-specific policies *because* of these differences.  All we've really done here is list a bunch of different GPU workloads and said a few words about them.}
Modern GPU workloads differ in resource demands based on deployment contexts, making static, one-size-fits-all management policies ineffective. For example, under memory oversubscription, simply choosing the right eviction and prefetch policy can swing execution time by up to 73\%~\cite{ganguly2019interplay,park2025helm}. LLM inference alternates compute-intensive prefill phases with bandwidth-sensitive decoding, benefiting from specialized KV-cache eviction and stride-based prefetching strategies rather than default LRU schemes~\cite{sheng2023flexgen,kwon2023efficient}. In contrast, Graph Neural Network (GNN) training workloads involve irregular, pointer-chasing accesses where aggressive sequential prefetching improves performance significantly~\cite{lin2024towards,wang2016gunrock}, yet this same strategy is detrimental to workloads dominated by random memory accesses. Similarly, GPU-based vector search shifts dynamically between sequential index construction and random query traversal phases~\cite{pan2024survey,cao2023gpu}, requiring phase-aware memory management. Even within single deployments, optimal policies vary over time as workloads and multi-tenant demands fluctuate, rendering static, deploy-time policies insufficient. \Cref{fig:access_patterns} illustrates this diversity: page fault patterns range from sequential scans (FAISS build) to sparse random accesses (MoE decode), requiring different prefetch strategies. Beyond memory, GPU-internal scheduling also exhibits workload-dependent imbalances: \Cref{fig:thread_scheduling} shows a 127$\times$ SM load imbalance in a vector-add kernel, invisible to host-side drivers. The dynamic nature of GPU workloads and their conflicting resource demands require runtime-adaptive, workload-specific GPU resource management policies.

\subsection{Agent-Based Policy Exploration}
\label{sec:motivation-agent}

GPU resource management often relies on heuristics or static policies designed based on developer experience and empirical trials. While suitable for many scenarios, these approaches become increasingly limited as workloads diversify or evolve. Manually exploring the large, workload-dependent policy space is costly and challenging.

Agent-based policy exploration offers an alternative. AI agents\cite{dwivedula2025policysmith,zheng2025schedcp} can iteratively generate policy candidates, evaluate their performance, and refine them based on feedback. Unlike traditional parameter-tuning methods, agents directly generate and adapt policy logic, exploring richer strategies tailored to specific workloads. This approach is effective for compiler heuristics~\cite{alphaevolve2025}, datacenter scheduling, LLM-serving policies~\cite{hamadanian2025glia,cheng2025barbarians}, and also eBPF programs~\cite{dwivedula2025policysmith,zheng2025schedcp}, thus showing potential for GPU resource management. However, without a safe OS interface, agent-generated policies risk kernel panics or GPU hangs from buggy code; with only user-space APIs, agents cannot explore driver-level decisions such as eviction ordering or fault-path prefetching.

To enable effective agent-driven GPU policy optimization and also benefit human developers, we require an OS interface with three key properties: \textbf{dynamic and transparent policy loading}, so agents can rapidly deploy and iterate policies at runtime without restarting applications or rebuilding kernel modules; \textbf{programmable policy logic}, to express flexible heuristics beyond fixed configuration knobs; \textbf{safety and isolation}, to robustly handle automatically generated candidate policies without crashing kernels or corrupting GPU device states. %No existing GPU resource management interface simultaneously meets these goals, motivating the need for a new OS abstraction tailored specifically to GPU extensions.

\subsection{Limitations of Existing Approaches}
\label{sec:motivation-limitations}

Existing approaches impose a tradeoff between programmability and control, failing to provide a dynamic, programmable, and safe OS interface for GPU resource management.

\paragraph{Driver-Level Policies.}
At the driver level, GPU resource management is controlled either through fixed configuration knobs (e.g., \texttt{cudaMemAdvise}, driver module parameters), which are safe but limited to selecting among preset behaviors, or through direct code modifications. Systems like TimeGraph~\cite{kato2011timegraph}, Gdev~\cite{kato2012gdev}, and kernel interception methods~\cite{kernelintercept} embed customized scheduling and memory-management logic into kernel-space or user-space driver modules. More recent work such as GPREEMPT~\cite{fan2025gpreempt} and GCAPS~\cite{wang2024gcaps} adds priority-based preemption to GPU drivers, and LithOS~\cite{coppock2025lithos} re-implements runtime stacks with OS-like abstractions. Despite improved performance, all these approaches embed specific policies requiring kernel or driver modifications to change, making them neither safely iterable nor rapidly deployable.

\paragraph{Host User-Space Runtimes and Libraries.}
Recent frameworks~\cite{ng2023paella,gim2025pie,shen2025xsched,chen2025ktransformers,coppock2025lithos} expose programmable GPU scheduling and memory management at the user-space layer. Despite this programmability, user-space systems share three limitations.
First, programmability remains application-bound: developers must write policies for a specific framework or runtime, often requiring code changes or porting applications onto specialized stacks, preventing reuse across ecosystems.
Second, user-space runtimes, confined to isolated process silos, lack global visibility across the coupled memory-scheduling domains and cannot coordinate across multi-tenant environments~\cite{xiao2018gandiva,yu2020fine}. Hardware partitioning such as NVIDIA's Multi-Instance GPU (MIG) imposes fixed resource boundaries that cannot be dynamically rebalanced.
Third, user-space frameworks lack privileged access to low-level driver mechanisms, leaving policies constrained to coarse-grained GPU kernel launch boundaries. This precludes precise preemption for latency-sensitive tasks and prevents fine-grained compute-transfer overlap. Moreover, they cannot execute policy logic on latency-critical paths (e.g., page-fault handlers), nor exploit GPU-side warp-level or barrier-level access patterns.

\subsection{GPU-Specific Challenges for eBPF Extensibility}
\label{sec:motivation-challenges}

eBPF has enabled safe runtime extensibility for CPU scheduling~\cite{schedext-docs} and page caching~\cite{zussman2025cache_ext}, making it a natural starting point for in-driver GPU extensibility. However, CPU-side eBPF extensibility (\S\ref{sec:background}) does not directly transfer to GPUs. Beyond the lack of safe programmable extension points in GPU drivers, three mismatches between the CPU eBPF model and GPU architecture create challenges without direct counterparts in CPU extensibility.
First, \emph{cross-device latency}: CPU eBPF callbacks execute synchronously, but GPU operations such as page migration cross the PCIe boundary and take milliseconds (\S\ref{sec:arch-gpu}). Policies must initiate transitions asynchronously and act proactively, not only reactively at the fault.
Second, \emph{memory-scheduling coupling}: CPU extensibility treats scheduling and memory as independent subsystems (\texttt{sched\_ext} and \texttt{cache\_ext}), but on GPU, limited device memory tightly couples these domains, as a page fault is simultaneously a memory event and a scheduling stall. GPU policies must coordinate across both.
Third, \emph{fragmented visibility}: CPU eBPF runs on the same processor it manages and observes every syscall and context switch, but in GPU stacks, policy-relevant state is split across layers with far less visibility at any single point. Downward, GPU-internal execution state such as per-warp access patterns, SM utilization, and thread block scheduling remains opaque to the host (\S\ref{sec:arch-gpu}). Upward, GPU runtimes bypass the kernel for multiple operations and policies (e.g., submit work via user-space command buffers and doorbells), so the driver sees only coarse Time-Slice Group (TSG) lifecycle events, not individual kernel launches or application phase transitions (e.g., LLM prefill-to-decode, FAISS build-to-search).
Naively exposing low-level GPU driver controls without addressing these mismatches risks resource leaks, hardware hangs, or kernel panics.

\paragraph{Binary Instrumentation on Device.}
Tools such as NVBit~\cite{villa2019nvbit} and Neutrino~\cite{neutrino} address fragmented visibility by injecting logic directly into GPU binaries. NVBit supports dynamic SASS-level instrumentation, while Neutrino provides instruction-level profiling via programmable assembly-layer probes with an eBPF-like interface. Despite this device-side visibility, these tools lack safety guarantees (injected logic can cause crashes or deadlocks), target offline profiling rather than online policy enforcement, and cannot coordinate policies across processes or with host-side drivers. Moreover, on NVIDIA GPUs, GPU kernels execute in warps of 32 threads that must follow uniform control paths; naively running scalar instrumentation logic per thread introduces warp divergence, serialization overhead, and prohibitive cost. A prior workshop paper eGPU~\cite{egpu} extends eBPF to GPU instrumentation but remains limited to read-only observability with high overhead (see \S\ref{sec:eval}).

\medskip
\noindent In summary, no existing approach provides a GPU resource management interface that is simultaneously programmable, safe for iterative exploration, and capable of addressing the cross-device latency, memory-scheduling coupling, and fragmented visibility inherent in GPU systems.

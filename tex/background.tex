\section{Background}

\subsection{GPU Systems Architecture}
\label{sec:arch-gpu}

Modern GPU software stacks consist of three major layers: \textbf{User-space logic (applications and runtimes)} includes high-level frameworks (e.g., PyTorch) and runtimes (e.g., CUDA libraries), managing operation graphs, tensor layouts, and command submissions via memory-mapped interfaces or ioctl calls to drivers; these encode rich semantic information such as neural network structures and latency constraints, with runtime systems like vLLM~\cite{kwon2023efficient}, fine-grained sharing frameworks such as Salus~\cite{yu2020fine}, and UVM-focused runtimes like PILOT~\cite{ravi2021pilot} implementing resource management policies at application level. \textbf{The kernel driver} acts as the OS component, managing privileged hardware mechanisms including the Memory Management Unit (MMU), hardware interrupts, and kernel scheduling, with host and device communication over PCIe incurring millisecond-scale latencies; under Unified Virtual Memory (UVM), applications allocating data beyond device memory capacity cause page faults, prompting driver-managed data migrations between host and device, making memory placement and compute scheduling interdependent—typical drivers implement application-agnostic algorithms such as LRU-based page eviction, round-robin context scheduling, and tree-based prefetching~\cite{gu2020uvmbench,amd-oversubscription}. \textbf{Device-side execution} occurs via user-defined device kernels and proprietary vendor firmware, compiled into static binaries with precise thread-level SIMT behaviors managed by GPU hardware schedulers at warp granularity; critical device-internal state, including per-warp access patterns, SM utilization, and thread-block progress, remains opaque to host-side drivers.

\subsection{eBPF and Kernel Extensibility}
\label{sec:background}

% Moved from "Limitations" — CPU eBPF paragraph, reframed as background on eBPF
eBPF (extended Berkeley Packet Filter) allows user-supplied programs to run safely inside the OS kernel. Programs are statically verified at load time for termination, memory safety, and type correctness, then JIT-compiled to native code. The verifier guarantees that programs access only permitted memory regions and call only approved kernel functions (helper or kfuncs). Programs attach to kernel-defined hook points via mechanisms such as \texttt{struct\_ops}, where the kernel invokes BPF callbacks at specific decision points and falls back to default behavior if no program is loaded. This mechanism has enabled runtime-programmable extensions to kernel subsystems: \texttt{sched\_ext}~\cite{schedext-docs} makes CPU scheduling programmable and \texttt{cache\_ext}~\cite{zussman2025cache_ext} extends page cache eviction via \texttt{struct\_ops}; XDP attaches eBPF programs at the network driver level to process packets. In these systems, each BPF callback makes a single synchronous decision at one transition point, with effects taking place immediately on local CPU resources, and each subsystem (scheduling, memory, networking) is extended independently.

Modern GPU systems run diverse workloads whose conflicting resource demands require different management policies. Under memory oversubscription, the choice of eviction and prefetch policy alone can control up to 73\% of execution time~\cite{ganguly2019interplay}, with similar magnitudes reported across GPU memory management workloads~\cite{park2025helm,kehne2019etc}.
LLM inference alternates between compute-intensive prefill and bandwidth-bound decoding~\cite{zhong2024distserve,patel2024splitwise}, with irregular KV-cache offloading~\cite{sheng2023flexgen,kwon2023efficient} and sparse MoE expert activations~\cite{gale2023megablocks,he2021fastmoe} that benefit from expert-aware eviction and stride-based prefetching; the default LRU eviction and tree-based prefetching in the driver perform poorly.
GNN training exhibits irregular, pointer-chasing accesses~\cite{lin2024towards,wang2016gunrock} where aggressive sequential prefetching helps, yet the same strategy harms random-access workloads.
Vector search has two distinct phases: index construction scans data sequentially, while query traversal follows random access patterns~\cite{pan2024survey,cao2023gpu}, requiring phase-adaptive prefetch policies.
These distinct memory behaviors (\Cref{fig:access_patterns}) and imbalanced thread scheduling across SMs (\Cref{fig:thread_scheduling}) demonstrate that no single eviction, prefetch, or scheduling policy fits all workloads. Moreover, optimal policies change at runtime: vector search alternates phases, multi-tenant mixes shift as jobs arrive and depart, and oversubscription ratios vary dynamically, making static policy selection at deploy time insufficient. In multi-tenant environments, latency-critical inference conflicts with throughput-maximizing training, creating contention that per-tenant priority differentiation can resolve but fixed partitioning cannot~\cite{xiao2018gandiva,yu2020fine}.

\subsection{Agent-Based Policy Exploration}
\label{sec:motivation-agent}

AI agents are increasingly capable of generating system policy code, not merely tuning configurations. Recent work demonstrates agents generating compiler heuristics~\cite{alphaevolve2025}, datacenter scheduling and LLM serving code~\cite{hamadanian2025glia,cheng2025barbarians}, and eBPF policies for congestion control and CPU scheduling~\cite{dwivedula2025policysmith,zheng2025schedcp}. GPU resource management, with its large policy space and workload-dependent optima, is a natural target for such exploration.

To be effective in this domain, agents require an interface that is dynamic, programmable and safe. This policy interface benefits human developers as well, but agents amplify the need by exploring at a pace where manual safety review become harder. Dynamic, because policies must be loadable and replaceable at runtime in milliseconds, without restarting applications or rebuilding kernel modules. Programmable, because agents generate policy \emph{code} (e.g., eviction ordering functions, prefetch strategies), not parameter vectors; fixed configuration knobs cannot express what agents produce. Safe, because agents explore iteratively, generating tens to hundreds of candidate policies, some of which may be incorrect; the interface must contain errors without crashing the kernel or corrupting device state. No existing GPU policy interface provides all three properties. Moreover, agents generating GPU policies must contend with GPU-specific architectural challenges that further constrain the interface design (\S\ref{sec:motivation-limitations}).

\subsection{Limitations of Existing Extensibility Mechanisms}
\label{sec:motivation-limitations}

Existing approaches each fail to provide a dynamic, programmable, and safe interface. Fixed configuration knobs and advisory hints (e.g., \texttt{cudaMemAdvise}, driver module parameters) are safe but not programmable: they select among preset behaviors and cannot express custom policy logic. Beyond these knobs:

\paragraph{Driver-Level Kernel-Space Policies.}

Systems like TimeGraph~\cite{kato2011timegraph}, Gdev~\cite{kato2012gdev}, and kernel interception methods~\cite{kernelintercept} embed customized scheduling and memory-management logic into kernel-space or user-space driver modules. More recent work such as GPREEMPT~\cite{fan2025gpreempt} and GCAPS~\cite{wang2024gcaps} adds priority-based preemption to GPU drivers, and LithOS~\cite{coppock2025lithos} re-implements runtime stacks with OS-like abstractions. Despite improved performance, all these approaches embed specific policies requiring kernel or driver modifications to change, making them neither safely iterable nor rapidly deployable.

\paragraph{Host User-Space Runtimes and Libraries}
Recent frameworks~\cite{ng2023paella,gim2025pie,shen2025xsched,chen2025ktransformers,coppock2025lithos} expose programmable GPU scheduling and memory management at the user-space layer. Despite this programmability, user-space systems share three limitations.
First, programmability remains application-bound: developers must write policies for a specific framework or runtime, often requiring code changes or porting applications onto specialized stacks, preventing reuse across ecosystems.
Second, user-space runtimes, confined to isolated process silos, lack global visibility across the coupled memory-scheduling domains and cannot coordinate across multi-tenant environments~\cite{xiao2018gandiva,yu2020fine}. Hardware partitioning such as NVIDIA's Multi-Instance GPU (MIG) imposes fixed resource boundaries that cannot be dynamically rebalanced.
Third, user-space frameworks lack privileged access to low-level driver mechanisms, leaving policies constrained to coarse-grained GPU kernel launch boundaries. This precludes precise preemption for latency-sensitive tasks and prevents fine-grained compute-transfer overlap. Moreover, they cannot execute policy logic on latency-critical paths (e.g., page-fault handlers), nor exploit GPU-side warp-level or barrier-level access patterns.

\paragraph{Host-Side eBPF Extensibility}
CPU-side eBPF extensibility (\S\ref{sec:background}) does not directly transfer to GPUs. Beyond the lack of safe programmable extension points in GPU drivers, three mismatches between the CPU eBPF model and GPU architecture create challenges without direct counterparts in CPU extensibility.
First, \emph{cross-device latency}: CPU eBPF callbacks execute synchronously, but GPU operations such as page migration cross the PCIe boundary and take milliseconds (\S\ref{sec:arch-gpu}). Policies must initiate transitions asynchronously and act proactively, not only reactively at the fault.
Second, \emph{memory-scheduling coupling}: CPU extensibility treats scheduling and memory as independent subsystems (\texttt{sched\_ext} and \texttt{cache\_ext}), but on GPU, limited device memory tightly couples these domains, as a page fault is simultaneously a memory event and a scheduling stall. GPU policies must coordinate across both.
Third, \emph{device opacity}: CPU eBPF runs on the same processor it manages, but host-based eBPF treats the GPU as a black box, unable to observe device-internal state such as per-warp access patterns and SM utilization (\S\ref{sec:arch-gpu}).
Naively exposing low-level GPU driver controls without addressing these mismatches risks resource leaks, hardware hangs, or kernel panics.

\paragraph{Binary Instrumentation and Profiling Tools on Device}
Tools such as NVBit~\cite{villa2019nvbit} and Neutrino~\cite{neutrino} address device opacity by injecting logic directly into GPU binaries. NVBit supports dynamic SASS-level instrumentation, while Neutrino provides instruction-level profiling via programmable assembly-layer probes with an eBPF-like interface. Despite this device-side visibility, these tools lack safety guarantees (injected logic can cause crashes or deadlocks), target offline profiling rather than online policy enforcement, and cannot coordinate policies across processes or with host-side drivers. Moreover, GPU kernels execute in warps of 32 threads that must follow uniform control paths; naively running scalar instrumentation logic per thread introduces warp divergence, serialization overhead, and prohibitive cost. A prior workshop paper eGPU~\cite{egpu} extends eBPF to GPU instrumentation but remains limited to read-only observability with high overhead (see \S\ref{sec:eval}).

\medskip
\noindent In summary, no existing approach provides a GPU resource management interface that is simultaneously programmable, safe for iterative exploration, and capable of addressing the cross-device latency, memory-scheduling coupling, and device opacity inherent in GPU systems.

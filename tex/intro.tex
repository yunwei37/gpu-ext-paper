\begin{abstract}
Performance in modern GPU-centric systems increasingly depends on resource management policies, including memory placement, scheduling, and observability. However, uniform policies typically yield suboptimal performance across diverse workloads. Existing approaches present a tradeoff: user-space runtimes provide programmability and flexibility but lack cross-tenant visibility and fine-grained control of hardware resources; meanwhile, modifications to the OS kernel introduce significant complexity and safety risks. 

To address this, we argue that the GPU driver and device layer should provide an extensible OS interface for policy enforcement. While the emerging eBPF technology shows potential, directly applying existing host-side eBPF is insufficient because they lack visibility and control into critical device-side events, and directly embedding policy code into GPU kernels could compromise safety and efficiency. \arq{We said that we want an extensible OS interface, what's the connection to this second sentence?  Why are we bringing up eBPF? Why does eBPF have these issues?  There's a big gap between the previous sentence and this one}
We propose \sys, an eBPF-based runtime that treats the GPU driver and device as a programmable OS subsystem. \sys extends GPU drivers by exposing safe programmable hooks and introduces a device-side eBPF runtime capable of executing verified policy logic within GPU kernels, enabling coherent and transparent policies. Evaluation across realistic workloads including inference, training, and vector search demonstrates that \sys improves throughput by up to $4.8\times$ and reduces tail latency by up to $2\times$, incurring minimal overhead, without modifying or restarting applications.
\end{abstract}

% P3: eBPF as the right tool, CPU precedent
To address this, we propose treating GPU resource management as a programmable OS subsystem, using eBPF to provide the safety and programmability that existing approaches lack. eBPF offers verified safety (sandboxed execution, guaranteed termination), arbitrary programmability, kernel-level access, and runtime deployability without recompilation. These are precisely the properties that kernel modifications sacrifice for control, and that user-space frameworks sacrifice for programmability. Recent CPU-side eBPF frameworks such as sched\_ext and cache\_ext have demonstrated the feasibility of this approach for CPU scheduling and page caching~\cite{bachl2021flow,Zhong22,jia2023programmable,schedext-docs,zussman2025cache_ext}.

% P4a: Co-location insight + two mismatches
However, the GPU is a discrete processor with its own ISA and execution model, and the policy executor (host driver) and the managed resource (device memory, GPU execution) sit on opposite sides of this divide. This breaks the co-location assumption that underlies CPU extensibility frameworks, where policy decisions and their effects share a single execution context. Two mismatches result.
\textbf{Timescale mismatch:} the synchronous callback model that suffices for CPU scheduling and page caching cannot express GPU policies whose effects outlive the callback. The most impactful operations (cross-block DMA migration, GPU preemption) take milliseconds because data must physically move between host and device memory, while the policy decision must return in microseconds. Furthermore, the fault handler is reactive (fires after faults), but optimal GPU policy is often proactive: prefetch before an epoch boundary, preempt before a latency-critical kernel launch. Because data must be physically moved, every page fault involves both a memory migration decision and a scheduling stall, coupling memory management and compute scheduling through the fault handler in a way that CPU subsystems (sched\_ext, cache\_ext) do not experience.
\textbf{Information mismatch:} the host cannot observe GPU execution state (per-warp access patterns, SM utilization, computation phases) without device-side instrumentation. Unlike the timescale mismatch, which shrinks with faster interconnects, this mismatch is permanent: the GPU's distinct ISA and execution model make its internal state architecturally opaque to the host regardless of interconnect latency.
A richer synchronous callback (e.g., returning DMA descriptors) would not resolve these mismatches; the issue is that policy effects outlive the callback, optimal timing precedes the fault, and device state requires device-side code to observe (\S\ref{sec:eval}).

% P4b: Mechanism mapping
\sys{} addresses each mismatch with composable mechanisms. For the timescale mismatch: synchronous advisory hooks in the fault handler provide the policy foundation; asynchronous sleepable kfuncs and BPF work queues initiate effects that outlive the callback (\S\ref{sec:design-interfaces}); and proactive uprobes on unmodified CUDA APIs trigger policies before events occur rather than after (\S\ref{sec:design-interfaces}). For the information mismatch: device-side BPF instrumentation extends eBPF to GPU hardware, closing the observation loop between device and host. Extending eBPF to SIMT hardware requires a new verifier that distinguishes warp-uniform from lane-varying values to prevent divergence and deadlocks (\S\ref{sec:verification}). Throughout, we balance expressiveness against stability with a narrow policy interface built around hardware-aligned abstractions (\S\ref{sec:design-interfaces}).

We implement \sys{} on Linux by extending the NVIDIA open GPU kernel modules~\cite{nvidia-open-gpu} and providing an eBPF runtime for GPU devices. We evaluate \sys across GPU workloads including LLM inference pipelines, GNN training, vector search, and mixed-priority multi-tenant scenarios. Using \sys, we implement adaptive memory prefetching and eviction policies, fine-grained kernel preemption strategies, dynamic work-stealing schedulers, and programmable GPU kernel observability tools. \sys-based policies improve throughput by up to $4.8\times$ and reduce tail latency by up to $2\times$ compared to static heuristics, with each mechanism layer adding measurable value: advisory hooks alone achieve $2.60\times$ on GNN training; adding the async path achieves $3.36\times$ (+27\%); adding proactive preemption further reduces multi-tenant tail latency. Instrumentation-only deployments incur low overhead. This demonstrates that cross-layer eBPF-based programmability spanning host and device is an effective abstraction for GPU-centric systems. All evaluated policies were generated by an AI agent as 59 eBPF program policy implementations across four workloads, with zero kernel panics, validating that eBPF's safety guarantees extend to the GPU stack. In summary, our contributions are:

\begin{itemize}[leftmargin=*,itemsep=0pt]
  \item We design an extensible OS policy interface for GPU memory, scheduling, and observability.

  \item We implement \sys, an eBPF runtime spanning host driver and GPU device, with three composable mechanism layers crossing the sync/async, driver/application, and host/device boundaries, and a SIMT-aware device-side verifier.

  \item We validate across four GPU workloads that each mechanism layer adds measurable value, achieving up to $4.8\times$ throughput improvement and $2\times$ tail latency reduction over static heuristics.
\end{itemize}

\begin{abstract}
Performance in modern GPU-centric systems increasingly depends on resource management policies, including memory placement, scheduling, and observability. However, uniform policies typically yield suboptimal performance across diverse workloads. Existing approaches present a tradeoff: user-space runtimes provide programmability and flexibility but lack cross-tenant visibility and fine-grained control of hardware resources; meanwhile, modifications to the OS kernel introduce significant complexity and safety risks. To address this, we argue that the GPU driver and device layer should provide an extensible OS interface for policy enforcement. While the emerging eBPF technology shows potential, directly applying existing host-side eBPF is insufficient because they lack visibility and control into critical device-side events, and directly embedding policy code into GPU kernels could compromise safety and efficiency.
We propose \sys, an eBPF-based runtime that treats the GPU driver and device as a programmable OS subsystem. \sys extends GPU drivers by exposing safe programmable hooks and introduces a device-side eBPF runtime capable of executing verified policy logic within GPU kernels, enabling coherent and transparent policies. Evaluation across realistic workloads including inference, training, and vector search demonstrates that \sys improves throughput by up to $4.8\times$ and reduces tail latency by up to $2\times$, incurring minimal overhead, without modifying or restarting applications.
\end{abstract}

GPU resource management policies have large, workload-dependent performance impact, and AI agents are actively optimizing such policies across the systems stack~\cite{cheng2025barbarians,hamadanian2025glia,liu2025systemint,zheng2025schedcp,alphaevolve2025,ding2025asap}. Default memory and scheduling policies perform poorly across diverse deployments spanning inference~\cite{kwon2023efficient,agrawal2024taming}, training~\cite{shoeybi2019megatron,rasley2020deepspeed}, graph analytics~\cite{lin2024towards,wang2016gunrock}, and vector search~\cite{pan2024survey,cao2023gpu}; recent work confirms this for UVM placement~\cite{wang2024suv,lin2025forest,kim2025dream,park2025helm} and scheduling~\cite{wang2024gcaps,fan2025gpreempt,shen2025xsched}, and the optimal choice varies with workload, hardware, and deployment context. Under memory oversubscription, for example, the choice of eviction and prefetch policy alone controls up to 73\% of execution time~\cite{park2025helm,kehne2019etc,ganguly2019interplay}.

GPU resource management policy must reside in the kernel driver---the only layer with global visibility across all processes, hardware privilege over page tables and scheduling, and authority to coordinate across tenants. But unlike CPU subsystems where policy decisions and their effects are co-located in a single execution context, GPU resource management spans a physical boundary: the GPU is a separate processor connected via PCIe, and policy decisions in the host driver are separated from their effects in time (microsecond decisions vs.\ millisecond DMA), space (host vs.\ device memory), and execution context (synchronous fault handler vs.\ asynchronous transfer engine). This separation limits not just how policies execute, but which policies can be expressed at all---confining agents to a narrow region of the policy space regardless of how they search. Beyond expressiveness, agents require runtime deployability, safety containment of failed policies, and fast iteration---properties that existing GPU approaches also lack.
Concretely, user-space frameworks~\cite{ng2023paella,shen2025xsched,gim2025pie,chen2025ktransformers} offer programmability, but lack cross-application visibility and management of low-level GPU mechanisms (e.g. thread timeslices and replayable page faults~\cite{fan2025gpreempt,nvidia-open-gpu}). These approaches bind to specific runtime frameworks, requiring application-level code changes and limiting portability and reuse. Conversely, kernel-based resource management approaches~\cite{kato2011timegraph,kato2012gdev,kernelintercept,fan2025gpreempt,wang2024gcaps} provide visibility and control of GPU hardware states, but their direct modification of static, vendor-specific kernel modules makes them difficult to deploy and maintain, and poses stability concerns. GPU profiling frameworks~\cite{cupti,villa2019nvbit,neutrino}, including our prior workshop version~\cite{egpu}, enable kernel-level observation but lack runtime programmability and driver integration, limiting adaptive resource management.

To address this, we argue that GPU resource management requires \textbf{an
OS policy interface for GPU} providing safe, flexible and transparent programmability. The GPU driver layer is uniquely positioned to offer global visibility, enable cross-tenant coordination, and provide fine-grained management of privileged low-level GPU mechanisms without requiring application modifications. Recent CPU-side eBPF frameworks such as sched\_ext and cache\_ext have demonstrated the feasibility of dynamic, kernel-level policy programmability with safety guarantees~\cite{bachl2021flow,Zhong22,jia2023programmable,schedext-docs,zussman2025cache_ext}. Building on this struct\_ops model, we adopt synchronous advisory hooks in the GPU driver as our starting point.

However, the synchronous, single-layer callback model that suffices for CPU scheduling and page caching leaves significant GPU performance unrealized. Advisory hooks capture only a fraction of the achievable improvement; the remainder requires asynchronous cross-boundary migration and proactive preemption---mechanisms that a synchronous callback cannot express (\S\ref{sec:eval}).

Three properties of GPU resource management, absent from prior eBPF extensibility targets, explain why. \textbf{Timescale mismatch:} the policy decision must return in microseconds (fault-handler context), but the most impactful operations---cross-block migration, GPU preemption---take milliseconds; a synchronous hook cannot initiate these and wait for completion. \textbf{Information mismatch:} the driver sees page faults but not application intent; optimal policy timing is often \emph{proactive}---preempt before a latency-critical kernel launch, prefetch before an epoch boundary---yet driver hooks fire only \emph{after} events occur. \textbf{Visibility mismatch:} the host controls memory placement and scheduling but cannot observe per-warp access patterns, SM utilization, or computation phases inside the GPU; conversely, the device observes execution but cannot control host resources. Each mismatch requires a distinct mechanism; no single callback model addresses all three.

We present \sys{}, a cross-layer policy runtime that transforms the GPU driver and device into a programmable OS subsystem, enabling safe runtime policy exploration. \sys{} provides three composable mechanism layers, each crossing one of the above boundaries: synchronous advisory hooks composed with asynchronous kernel work queues, for policies whose decisions are fast but whose effects (cross-block migration, GPU preemption) take milliseconds (\S\ref{sec:design-interfaces}); proactive triggers on unmodified application APIs, for policies that must act on application intent before driver events occur (\S\ref{sec:design-interfaces}); and device-side instrumentation that extends eBPF to GPU hardware, closing the observation-action loop between device and host. Extending eBPF to SIMT hardware requires a new verifier that distinguishes warp-uniform from lane-varying values to prevent divergence and deadlocks (\S\ref{sec:verification}).


We implement \sys{} on Linux by extending the NVIDIA open GPU kernel modules~\cite{nvidia-open-gpu} and providing an eBPF runtime for GPU devices. We evaluate \sys across GPU workloads including LLM inference pipelines, GNN training, vector search, and mixed-priority multi-tenant scenarios. Using \sys, we implement adaptive memory prefetching and eviction policies, fine-grained kernel preemption strategies, dynamic work-stealing schedulers, and programmable GPU kernel observability tools. \sys-based policies improve throughput by up to $4.8\times$ and reduce tail latency by up to $2\times$ compared to static heuristics, with each mechanism layer adding measurable value: advisory hooks alone achieve $2.60\times$ on GNN training; adding the async path achieves $3.36\times$ (+27\%); adding proactive preemption further reduces multi-tenant tail latency. Instrumentation-only deployments incur low overhead. This demonstrates that cross-layer eBPF-based programmability spanning host and device is an effective abstraction for GPU-centric systems. In our experiments, AI agents used \sys's BPF interface to explore 59 policies with zero kernel panics, validating the safety of the exploration loop. In summary, our contributions are:

\begin{itemize}[leftmargin=*,itemsep=0pt]
  \item We design an extensible OS policy interface for GPU memory, scheduling, and observability.

  \item We implement \sys, an eBPF runtime spanning host driver and GPU device, with three composable mechanism layers crossing the sync/async, driver/application, and host/device boundaries, and a SIMT-aware device-side verifier.

  \item We validate across four GPU workloads that each mechanism layer adds measurable value, achieving up to $4.8\times$ throughput improvement and $2\times$ tail latency reduction over static heuristics.
\end{itemize}

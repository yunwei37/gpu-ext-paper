\begin{abstract}
Performance in modern GPU-centric systems increasingly depends on resource management policies, including memory placement, scheduling, and observability. However, uniform policies typically yield suboptimal performance across diverse workloads. Existing approaches present a tradeoff: user-space runtimes provide programmability and flexibility but lack cross-tenant visibility and fine-grained control of hardware resources; meanwhile, modifications to the OS kernel introduce significant complexity and safety risks. To address this, we argue that the GPU driver and device layer should provide an extensible OS interface for policy enforcement. While the emerging eBPF technology shows potential, directly applying existing host-side eBPF is insufficient because they lack visibility and control into critical device-side events, and directly embedding policy code into GPU kernels could compromise safety and efficiency.
We propose \sys, an eBPF-based runtime that treats the GPU driver and device as a programmable OS subsystem. \sys extends GPU drivers by exposing safe programmable hooks and introduces a device-side eBPF runtime capable of executing verified policy logic within GPU kernels, enabling coherent and transparent policies. Evaluation across realistic workloads including inference, training, and vector search demonstrates that \sys improves throughput by up to $4.8\times$ and reduces tail latency by up to $2\times$, incurring minimal overhead, without modifying or restarting applications.
\end{abstract}

\section{Introduction}

% P1: GPU policy impact + diversity + agent exploration
GPU resource management policies have large, workload-dependent performance impact, and AI agents are actively optimizing such policies across the systems stack~\cite{cheng2025barbarians,hamadanian2025glia,liu2025systemint,zheng2025schedcp,alphaevolve2025,ding2025asap}. Default memory and scheduling policies perform poorly across diverse deployments spanning inference~\cite{kwon2023efficient,agrawal2024taming}, training~\cite{shoeybi2019megatron,rasley2020deepspeed}, graph analytics~\cite{lin2024towards,wang2016gunrock}, and vector search~\cite{pan2024survey,cao2023gpu}; recent work confirms this for UVM placement~\cite{wang2024suv,lin2025forest,kim2025dream,park2025helm} and scheduling~\cite{wang2024gcaps,fan2025gpreempt,shen2025xsched}, and the optimal choice varies with workload, hardware, and deployment context. Under memory oversubscription, for example, the choice of eviction and prefetch policy alone controls up to 73\% of execution time~\cite{park2025helm,kehne2019etc,ganguly2019interplay}.

% P2: Gap claim + existing approaches
No general-purpose, programmable OS extensibility interface exists for GPU resource management policy, a gap that grows more critical as AI agents evolve from configuration tuners to policy code writers~\cite{cheng2025barbarians,alphaevolve2025,zheng2025schedcp}. GPU resource management policy is coordinated in the kernel driver, the only layer with global visibility across all processes, hardware privilege over page tables and scheduling, and authority to coordinate across tenants. Yet this driver layer remains closed to external policy logic. User-space frameworks~\cite{ng2023paella,shen2025xsched,gim2025pie,chen2025ktransformers} offer programmability but lack cross-application visibility and low-level GPU control~\cite{fan2025gpreempt,nvidia-open-gpu}. Kernel driver modifications~\cite{kato2011timegraph,kato2012gdev,kernelintercept,fan2025gpreempt,wang2024gcaps} provide visibility and control but are fragile, vendor-specific, and unsafe for agent-generated code. GPU profiling frameworks~\cite{cupti,villa2019nvbit,neutrino}, including our prior workshop version~\cite{egpu}, enable observation but lack runtime programmability.

% P3a: eBPF as the right tool + struct_ops as starting point
To address this, we propose treating GPU resource management as a programmable OS subsystem, using eBPF to provide the safety and programmability that existing approaches lack. eBPF offers verified safety (sandboxed execution, guaranteed termination), arbitrary programmability, kernel-level access, and runtime deployability without recompilation. These are precisely the properties that kernel modifications sacrifice for control, and that user-space frameworks sacrifice for programmability. Recent CPU-side eBPF frameworks such as sched\_ext and cache\_ext have demonstrated the feasibility of this approach for CPU scheduling and page caching~\cite{bachl2021flow,Zhong22,jia2023programmable,schedext-docs,zussman2025cache_ext}. Building on this struct\_ops model, we adopt synchronous advisory hooks in the GPU driver as our starting point.

% P3b: But struct_ops insufficient + evidence
However, the synchronous, single-layer callback model that suffices for CPU scheduling and page caching leaves significant GPU performance unrealized. Advisory hooks capture only a fraction of the achievable improvement; the remainder requires asynchronous cross-boundary migration and proactive preemption, mechanisms that a synchronous callback cannot express (\S\ref{sec:eval}).

Three properties of GPU resource management, absent from prior eBPF extensibility targets, explain why. \textbf{Timescale mismatch:} the policy decision must return in microseconds (fault-handler context), but the most impactful operations (cross-block migration, GPU preemption) take milliseconds; a synchronous hook cannot initiate these and wait for completion. \textbf{Information mismatch:} the driver sees page faults but not application intent; optimal policy timing is often \emph{proactive}: preempt before a latency-critical kernel launch, prefetch before an epoch boundary. Yet driver hooks fire only \emph{after} events occur. \textbf{Visibility mismatch:} the host controls memory placement and scheduling but cannot observe per-warp access patterns, SM utilization, or computation phases inside the GPU; conversely, the device observes execution but cannot control host resources. Each mismatch requires a distinct mechanism; no single callback model addresses all three.

We present \sys{}, a cross-layer policy runtime that transforms the GPU driver and device into a programmable OS subsystem, enabling safe runtime policy exploration. \sys{} provides three composable mechanism layers, each crossing one of the above boundaries: synchronous advisory hooks composed with asynchronous kernel work queues, for policies whose decisions are fast but whose effects (cross-block migration, GPU preemption) take milliseconds (\S\ref{sec:design-interfaces}); proactive triggers on unmodified application APIs, for policies that must act on application intent before driver events occur (\S\ref{sec:design-interfaces}); and device-side instrumentation that extends eBPF to GPU hardware, closing the observation-action loop between device and host. Extending eBPF to SIMT hardware requires a new verifier that distinguishes warp-uniform from lane-varying values to prevent divergence and deadlocks (\S\ref{sec:verification}). Throughout, we balance expressiveness against stability with a narrow policy interface built around hardware-aligned abstractions (\S\ref{sec:design-interfaces}).


We implement \sys{} on Linux by extending the NVIDIA open GPU kernel modules~\cite{nvidia-open-gpu} and providing an eBPF runtime for GPU devices. We evaluate \sys across GPU workloads including LLM inference pipelines, GNN training, vector search, and mixed-priority multi-tenant scenarios. Using \sys, we implement adaptive memory prefetching and eviction policies, fine-grained kernel preemption strategies, dynamic work-stealing schedulers, and programmable GPU kernel observability tools. \sys-based policies improve throughput by up to $4.8\times$ and reduce tail latency by up to $2\times$ compared to static heuristics, with each mechanism layer adding measurable value: advisory hooks alone achieve $2.60\times$ on GNN training; adding the async path achieves $3.36\times$ (+27\%); adding proactive preemption further reduces multi-tenant tail latency. Instrumentation-only deployments incur low overhead. This demonstrates that cross-layer eBPF-based programmability spanning host and device is an effective abstraction for GPU-centric systems. In our experiments, AI agents generated and deployed 59 BPF policy programs, implementing eviction ordering, prefetch strategies, and scheduling logic, with zero kernel panics, validating that eBPF's safety guarantees extend to the GPU driver fault path. In summary, our contributions are:

\begin{itemize}[leftmargin=*,itemsep=0pt]
  \item We design an extensible OS policy interface for GPU memory, scheduling, and observability.

  \item We implement \sys, an eBPF runtime spanning host driver and GPU device, with three composable mechanism layers crossing the sync/async, driver/application, and host/device boundaries, and a SIMT-aware device-side verifier.

  \item We validate across four GPU workloads that each mechanism layer adds measurable value, achieving up to $4.8\times$ throughput improvement and $2\times$ tail latency reduction over static heuristics.
\end{itemize}

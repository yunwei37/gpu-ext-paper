\begin{abstract}
GPU resource management policies significantly influence application performance, yet optimal policies vary widely across workloads and deployment scenarios. Existing user-space solutions offer programmability and flexibility but lack cross-tenant visibility and hardware-level control, while kernel-driver modifications introduce complexity and safety risks, limiting deployment and AI agent policy exploration.
We introduce \sys, an OS interface for GPU resource management that resolves this tradeoff through safe, programmable eBPF extensions across the GPU kernel driver and device. Unlike existing CPU-focused policy interfaces which rely on synchronous callbacks and local resource control, \sys addresses GPU-specific challenges: high latency of cross-device coordination, coupling of memory management and scheduling decisions, and limited device observability. To overcome these, \sys models GPU resource management as programmable asynchronous effects on resource lifecycles, directed by verified eBPF programs and decoupling policy triggers from lifecycle transitions across the boundary. To further bridge the visibility gap, \sys enables safe eBPF execution directly on GPU hardware with a SIMT-aware verifier. Evaluated within the Linux NVIDIA GPU driver, AI-generated policies with \sys outperform existing GPU management approaches across diverse workloads, increasing throughput by up to 4.8× over framework offloading and reducing tail latency by up to 2× without application modifications or compromising stability.
\end{abstract}

\section{Introduction}
%  GPU resource management has become increasingly policy-sensitive: a policy that helps one workload can easily hurt another. For example, under memory oversubscription, aggressive prefetching can reduce stalls for LLM inference, yet the same policy may waste bandwidth and slow graph analytics; similarly, throughput-oriented scheduling can improve batch-oriented vector search while worsening tail latency for interactive inference. This variability reflects a broader trend across modern GPU workloads---including LLM inference and training, graph analytics, and vector search---which differ substantially in memory-access patterns, latency objectives, and compute-to-bandwidth balance~\cite{kwon2023efficient,agrawal2024taming,shoeybi2019megatron,rasley2020deepspeed,lin2024towards,wang2016gunrock,pan2024survey,cao2023gpu}. As a result, no single resource-management policy works well across workloads, phases, and deployment settings. Prior work shows that under memory pressure, policy choices such as eviction and prefetching alone can account for a large fraction of total execution time~\cite{wang2024suv,lin2025forest,kim2025dream,park2025helm,wang2024gcaps,fan2025gpreempt,shen2025xsched,kehne2019etc,ganguly2019interplay}. GPU resource management is therefore not just a fixed-policy problem; it is a policy-selection problem.
GPU resource management policies critically influence application performance, yet optimal memory and scheduling policies vary significantly across workloads, hardware, and deployment contexts. Default policies perform poorly for diverse scenarios~\cite{kwon2023efficient,agrawal2024taming,lin2024towards,wang2016gunrock,shoeybi2019megatron,rasley2020deepspeed,pan2024survey,cao2023gpu}: for example, aggressive prefetching can reduce stalls for LLM inference yet waste bandwidth and slow graph analytics, while throughput-oriented scheduling can improve vector search but worsen tail latency for interactive inference. Recent studies demonstrate this sensitivity for Unified Virtual Memory (UVM) placement~\cite{wang2024suv,lin2025forest,kim2025dream,park2025helm} and GPU scheduling~\cite{wang2024gcaps,fan2025gpreempt,shen2025xsched}. Under memory oversubscription, for instance, eviction and prefetch policy choice alone determines up to 73\% of total execution time~\cite{park2025helm,kehne2019etc,ganguly2019interplay}.

% Once GPU management becomes a policy-selection problem, the system must support not one policy, but the rapid exploration of many. Good policies depend on workload-specific structure: which pages will be reused, when memory pressure will arise, which requests are latency-critical, and which work should run, yield, or be preempted first. Exploring such policies manually is costly, so the system must make policy development and iteration practical. This need is only becoming more important as policy search becomes increasingly automated, including with AI-assisted methods~\cite{alphaevolve2025,hamadanian2025glia,cheng2025barbarians,ding2025asap,dwivedula2025policysmith,zheng2025schedcp}. For such exploration to be useful in production settings, however, the underlying interface must provide two properties at once: it must be \emph{programmable}, so that policies can be expressed and revised quickly, and it must be \emph{safe and verifiable}, so that buggy or automatically generated policies cannot crash the kernel, corrupt GPU state, or destabilize running applications.
Finding optimal GPU resource management policies requires exploring a vast policy space dependent on workload-specific characteristics, making it an ideal target for automated policy exploration by AI agents while costly for developers. Agents are increasingly capable of generating policy code, not just tuning parameters, including compiler heuristics~\cite{alphaevolve2025}, datacenter scheduling, LLM serving strategies~\cite{hamadanian2025glia,cheng2025barbarians}, training methods~\cite{ding2025asap}, and even eBPF programs~\cite{dwivedula2025policysmith,zheng2025schedcp}. To be effective, agents and human developers alike require a dynamic, programmable, and safe OS interface to iteratively deploy and evaluate generated policies, without modifying or restarting applications.



% This dual requirement exposes a gap in existing GPU software stacks. User-space runtimes and frameworks are programmable, but they do not control privileged mechanisms such as page-fault handling, page migration, page-table state, or fine-grained command scheduling~\cite{ng2023paella,shen2025xsched,gim2025pie,chen2025ktransformers,nvidia-open-gpu}. Because they operate above the driver boundary, they also lack global visibility across tenants and across tightly coupled memory and scheduling decisions. Kernel-driver mechanisms sit at exactly the right control point for these functions and naturally enforce safety and isolation, but they expose little runtime programmability: changing policy typically requires modifying driver code itself~\cite{kato2011timegraph,kato2012gdev,kernelintercept,fan2025gpreempt,wang2024gcaps}. Existing knobs and advisory APIs remain safe, but they can only select among predefined behaviors rather than express new policy logic. What is missing, therefore, is an OS interface that combines kernel-level visibility and control with safe runtime programmability.
Existing GPU resource management approaches impose a tradeoff. User-space frameworks~\cite{ng2023paella,shen2025xsched,gim2025pie,chen2025ktransformers} offer programmability but lack cross-application visibility and low-level hardware controls, such as page fault handling or precise command scheduling~\cite{nvidia-open-gpu}. Kernel-driver modifications~\cite{kato2011timegraph,kato2012gdev,kernelintercept,fan2025gpreempt,wang2024gcaps} provide this visibility and control but are fragile, vendor-specific, and unsafe for frequent or agent-driven updates. Fixed configuration knobs exposed by existing APIs are safe but limit what agents and developers can express.



% eBPF makes such an interface plausible because it already provides a model for safe kernel extensibility. User-defined logic can execute in privileged software while remaining constrained by static verification, typed interfaces, and trusted helper functions~\cite{schedext-docs,zussman2025cache_ext,bachl2021flow,Zhong22,jia2023programmable}. But GPU resource management cannot simply reuse the CPU eBPF model, because the challenge is shaped by GPU-specific execution constraints. First, GPU control paths are inherently \emph{cross-device}: decisions made in the host driver often take effect on a separate device, and operations such as migration, preemption, and dispatch can take microseconds to milliseconds, making purely synchronous callback-style control too rigid. Second, GPUs expose strong \emph{memory-scheduling coupling}: limited device memory and bandwidth tightly couple data placement with execution order, so memory and scheduling cannot be treated as independent extension points. Third, many useful policy signals remain hidden behind \emph{device opacity}: warp-level access patterns, stall behavior, and SM-level load imbalance are often visible only on the GPU itself. A programmable GPU policy interface must therefore be designed around GPU-specific execution constraints rather than inherited directly from CPU extensibility mechanisms.
We propose resolving this tradeoff by creating a programmable OS subsystem interface for GPU resource management. To achieve visibility and precise control, our subsystem integrates directly within the GPU kernel driver, the natural OS-level coordination point controlling cross-tenant hardware resources like page tables and scheduling. For safety, we leverage eBPF: an OS extensibility mechanism providing safe kernel-level programmability, allowing verified user-defined programs to dynamically replace hardcoded policies, which has been used for CPU scheduling~\cite{schedext-docs}, page caching~\cite{zussman2025cache_ext} and so on~\cite{schedext-docs,zussman2025cache_ext,bachl2021flow,Zhong22,jia2023programmable}.


% We present \sys, an OS interface for GPU resource management built around \emph{asynchronous programmable lifecycles}. The key idea is to separate \emph{policy decisions} from \emph{mechanism execution}. In \sys, verified eBPF programs decide \emph{when} a memory or scheduling transition should be initiated and under what conditions, but trusted kernel- and device-side mechanisms decide \emph{how} that transition executes. A trigger such as a fault, queue event, or device-side signal can therefore launch an asynchronous lifecycle---for example, eviction, prefetch, reprioritization, or preemption---that proceeds safely across the host-device boundary under kernel control. This abstraction directly addresses the constraints above: it decouples triggers from effects to tolerate cross-device latency, exposes memory and scheduling within one programmable interface to handle their coupling, and enables safe policy execution on the GPU itself to overcome device opacity.

However, directly applying the CPU eBPF model to GPU resource management is insufficient, because the GPU is a discrete processor with its own execution model and resources, and policy decisions in the host driver must take effect on a separate device. First, cross-device operations like migrating data or dispatching commands take milliseconds, too slow for synchronous callbacks and too costly for purely reactive decisions. Second, unlike independent subsystems on CPU, limited device memory and bandwidth further couple memory and scheduling, as decisions about data placement directly affect which workloads can execute. Third, policy-relevant state suffers from fragmented visibility across the stack: GPU-internal execution state is opaque to the host, while application intent is invisible to the driver as GPU runtimes bypass the kernel.

To address these challenges, \sys{} models GPU resource management as programmable \emph{effects} on resource lifecycles, where verified BPF programs direct transitions of both memory and scheduling (\S\ref{sec:design-interfaces}). Here, effects are kfunc-initiated transitions, such as eviction, prefetch, and preemption, along kernel-managed resource state machines, and lifecycles define the valid states and transitions for memory chunks and compute contexts. Unlike current policy interfaces such as sched\_ext, cache\_ext and XDP, where each callback makes one synchronous decision at one fixed transition point, \sys{} programs can direct multiple transitions asynchronously from user-defined triggers across the management stack, decoupling triggers from their effects across device and layer boundaries. To ensure safety, policies only influence which transitions occur and when, but cannot create invalid transitions or violate resource invariants. \sys{} extends this model to GPU-internal execution, where a SIMT-aware verifier enables verified BPF to run on GPU hardware for observation and policy execution (\S\ref{sec:verification}).

% To realize this model, \sys extends eBPF across both the Linux NVIDIA GPU driver and the device. It provides structured hooks for memory and scheduling events, trusted kfuncs for invoking controlled transitions, and hierarchical shared maps that allow device observations, host decisions, and asynchronous effects to compose into one policy loop. It also introduces a SIMT-aware verification and execution model for device-side eBPF, enabling safe execution under GPU warp semantics. We implement \sys in the Linux NVIDIA GPU driver and evaluate it on LLM inference, GNN training, vector search, and multi-tenant workloads. Across these settings, \sys policies improve throughput by up to $4.8\times$ and reduce tail latency by up to $2\times$, without application modifications or observed stability issues.
We implement \sys{} on Linux by extending the NVIDIA open GPU kernel modules~\cite{nvidia-open-gpu} and providing an eBPF runtime for both host driver and GPU device. We evaluate \sys{} across LLM inference, GNN training, vector search, and multi-tenant scenarios. \sys-based policies improve throughput by up to $4.8\times$ over framework offloading and $1.76\times$ over application-tuned baselines, and reduce tail latency by up to $2\times$, with low overhead and no application modifications or restarts.
In our experiments, AI agents generated all 59 evaluated BPF policies, including eviction ordering, prefetch strategies, scheduling logic, and device-side work-stealing, with zero kernel panics, validating that eBPF's safety guarantees extend to the GPU driver and device.

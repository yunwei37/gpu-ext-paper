\begin{abstract}
Performance in modern GPU-centric systems increasingly depends on resource management policies, including memory placement, scheduling, and observability. However, uniform policies typically yield suboptimal performance across diverse workloads. Existing approaches present a tradeoff: user-space runtimes provide programmability and flexibility but lack cross-tenant visibility and fine-grained control of hardware resources; meanwhile, modifications to the OS kernel introduce significant complexity and safety risks. 

To address this, we argue that the GPU driver and device layer should provide an extensible OS interface for policy enforcement. While the emerging eBPF technology shows potential, directly applying existing host-side eBPF is insufficient because they lack visibility and control into critical device-side events, and directly embedding policy code into GPU kernels could compromise safety and efficiency. \arq{We said that we want an extensible OS interface, what's the connection to this second sentence?  Why are we bringing up eBPF? Why does eBPF have these issues?  There's a big gap between the previous sentence and this one}
We propose \sys, an eBPF-based runtime that treats the GPU driver and device as a programmable OS subsystem. \sys extends GPU drivers by exposing safe programmable hooks and introduces a device-side eBPF runtime capable of executing verified policy logic within GPU kernels, enabling coherent and transparent policies. Evaluation across realistic workloads including inference, training, and vector search demonstrates that \sys improves throughput by up to $4.8\times$ and reduces tail latency by up to $2\times$, incurring minimal overhead, without modifying or restarting applications.
\end{abstract}

However, the GPU is a physically separate processor, so the policy executor (host driver) and the managed resource (device memory, GPU execution) opposite sides of this boundary. This physical separation breaks the co-location assumption that underlies CPU extensibility frameworks, where policy decisions and their effects share a single execution context. As a result, the synchronous, single-layer callback model that suffices for CPU scheduling and page caching leaves significant GPU performance unrealized: advisory hooks capture only a fraction of the achievable improvement, and the remainder requires asynchronous cross-boundary migration and proactive preemption, mechanisms that a synchronous callback cannot express (\S\ref{sec:eval}). Three mismatches, absent from prior eBPF extensibility targets, explain why. \textbf{Timescale mismatch:} the policy decision must return in microseconds (fault-handler context), but the most impactful operations (cross-block migration, GPU preemption) take milliseconds; a synchronous hook cannot initiate these and wait for completion. \textbf{Information mismatch:} the driver sees page faults but not application intent; optimal policy timing is often \emph{proactive}: preempt before a latency-critical kernel launch, prefetch before an epoch boundary. Yet driver hooks fire only \emph{after} events occur. \textbf{Visibility mismatch:} the host controls memory placement and scheduling but cannot observe per-warp access patterns, SM utilization, or computation phases inside the GPU; conversely, the device observes execution but cannot control host resources. Each mismatch requires a distinct mechanism; no single callback model addresses all three. \arq{There are some good ideas in this paragraph, although it is pretty complicated to disentangle. We present \sys{}, a cross-layer policy runtime that transforms the GPU driver and device into a programmable OS subsystem, enabling safe runtime policy exploration. \sys{} provides three composable mechanism layers, each crossing one of the above boundaries: synchronous advisory hooks composed with asynchronous kernel work queues, for policies whose decisions are fast but whose effects (cross-block migration, GPU preemption) take milliseconds (\S\ref{sec:design-interfaces}); proactive triggers on unmodified application APIs, for policies that must act on application intent before driver events occur (\S\ref{sec:design-interfaces}); and device-side instrumentation that extends eBPF to GPU hardware, closing the observation-action loop between device and host. Extending eBPF to SIMT hardware requires a new verifier that distinguishes warp-uniform from lane-varying values to prevent divergence and deadlocks (\S\ref{sec:verification}). Throughout, we balance expressiveness against stability with a narrow policy interface built around hardware-aligned abstractions (\S\ref{sec:design-interfaces}).\arq{The content is generally strong, but I think this needs to be "punchier". We implement \sys{} on Linux by extending the NVIDIA open GPU kernel modules~\cite{nvidia-open-gpu} and providing an eBPF runtime for GPU devices. We evaluate \sys across GPU workloads including LLM inference pipelines, GNN training, vector search, and mixed-priority multi-tenant scenarios.

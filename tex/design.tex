\section{\sys Design}

% Challenges C1/C2/C3 moved to §3 Motivation (sec:motivation-limitations)

\sys{} provides a safe, programmable OS interface for GPU resource management, supporting dynamic AI-generated policies transparently. As identified in \S\ref{sec:motivation-challenges}, achieving these goals requires addressing three GPU-specific challenges: (1) cross-device latency that necessitates asynchronous policy execution, (2) memory-scheduling coupling that demands unified lifecycle management across both domains, and (3) fragmented visibility across the stack that requires both device-side verified BPF execution and user-defined triggers to bridge the application-driver-device gap.

\subsection{\sys{} Policy Execution Model}
\label{sec:design-interfaces}

\subsubsection{Programmable Effects on Resource Lifecycles}

\sys models GPU resource management as programmable effects on resource lifecycles. GPU resources transition through defined lifecycles: memory chunks between activated, accessed, and evicted; compute contexts between created, scheduled, preempted, and finished; and on-device execution units (thread blocks and warps) between launched, executing, stalled, and completed.

To write a policy in \sys{}, developers implement eBPF programs that direct resource lifecycle transitions from user-defined events asynchronously via OS kernel functions (\emph{kfuncs}). Unlike prior BPF extensibility systems (e.g., sched\_ext, cache\_ext, XDP), which rely on fixed, synchronous callbacks returning immediate decisions, \sys{} decouples policy triggers from their cross-device effects. Triggers can originate from driver callbacks, application functions (uprobes), device-side execution events, and asynchronous tasks (\texttt{bpf\_wq}). Each trigger can produce multiple concurrent effects across memory and scheduling domains. For example, a uprobe at \texttt{cudaLaunchKernel} can asynchronously initiate a 6.6\,ms DMA prefetch informed by device-side observations while concurrently preempting another tenant's context to free GPU memory.

\sys defines three eBPF program types to control distinct resource domains: \texttt{GPU\_MEM} for memory placement, \texttt{GPU\_SCHED} for scheduling decisions, and \texttt{GPU\_DEV} for device-side execution. Memory placement is modeled as a programmable cache, exposing lifecycle events (\emph{activate}, \emph{access}, \emph{evict\_prepare}, \emph{prefetch}) on GPU-managed units (e.g., 2MB UVM chunks). Compute scheduling exposes TSG lifecycle events (\emph{task\_init}, \emph{task\_destroy}) and preemption at per-GPU-kernel granularity. Device-side eBPF cooperates with host-side policies by capturing fine-grained runtime state like access patterns or thread scheduling events, coordinating across domains via cross-layer maps, and enabling on-device decisions like block scheduling (e.g., warp-level work-stealing) or prefetch (e.g., device L2 prefetch triggers host callback for extended prefetch).

To ensure OS kernel safety boundaries, in \sys{}, verified kfuncs constrain lifecycle transitions to three dimensions: \emph{ordering} (evict chunk A before B), \emph{timing} (prefetch now rather than waiting), and \emph{selection} (preempt tenant X for Y), and the lifecycle is always managed by the driver mechanism. Policies can only reorder driver-maintained eviction lists, cannot allocate memory, and fall back to default FIFO behavior under pressure or misconfiguration. In multi-tenant settings, a single administrator-defined policy governs all tenants, as with sched\_ext; per-tenant policy isolation is future work.

\subsubsection{Example: MoE Expert Offloading}

We illustrate the programmable effects model with Mixture-of-Experts (MoE) offloading where model size is larger than GPU memory. As not all expert parameters fit in device memory, the GPU driver continuously evicts and migrates expert pages. Each token activates only a subset of experts, but the default driver's LRU eviction and tree-based prefetching lack visibility into expert activation patterns, causing costly PCIe DMA stalls on cold expert page faults.

A \sys{} policy uses three cooperating BPF programs at different layers (\Cref{fig:moe-listing}), coordinating via a shared cross-layer map. First, during GPU kernel execution, a device-side BPF handler inserted at warp entry tracks warp-level accesses to expert pages, recording per-page access counts for each warp in a hierarchical cross-layer map (visible only on-device). Second, a uprobe BPF program attached to \texttt{cuda\-Launch\-Kernel} proactively reads these counts to predict upcoming expert activations. It asynchronously initiates prefetches (\texttt{bpf\_gpu\_\allowbreak{}prefetch\_async}) to overlap memory migration with computation, avoiding expensive stalls. If memory pressure arises, this program can simultaneously preempt lower-priority GPU tasks via \texttt{gdrv\_sched\_\allowbreak{}preempt}. Finally, upon memory eviction (\emph{evict\_prepare}), a kernel-side BPF handler leverages the same expert access counts to evict cold pages first (LFU ordering), protecting hot experts. Unlike framework-level offloading that often migrates experts as atomic units, \sys operates at page granularity, enabling finer-grained compute-transfer overlap.
Each eBPF program exists because information resides in different layers; cross-layer maps coordinate them to orchestrate resource transitions across GPU and host boundaries.

As shown in Figure~\ref{fig:system-design}, policy authors use standard eBPF tooling (e.g., \texttt{clang/libbpf}, \texttt{bpftool}) to build a single policy object containing both host and device parts, and deploy it via a loader library that installs policies, configures maps, and supports runtime redeployment without  application or driver restarts. The runtime spans host driver and GPU device, managing verification (\S\ref{sec:verification}), JIT compilation to native host CPU code or GPU-compatible instructions (e.g., PTX), and hierarchical map placement across host and device.

\subsection{Runtime Verification and Optimizations}
\label{sec:verification}

\sys policies execute directly within privileged GPU driver and OS kernel contexts, making safety guarantees critical. The threat model follows standard eBPF: administrators are trusted, but policy code may be buggy or misconfigured. The trusted computing base (TCB) includes the OS kernel, \sys driver module, GPU compiler backend, and GPU driver/firmware. Host-side verification reuses the Linux eBPF verifier unchanged; \sys-specific kfuncs are declared via BTF metadata.

\subsubsection{SIMT-aware Verification}

Because the GPU executes in SIMT (Single Instruction, Multiple Threads) mode, device-side BPF programs must respect warp-level execution semantics, while preserving eBPF's scalar programming model to pass the verifier.. \sys introduces a SIMT-aware static verification model enforcing warp-level uniformity constraints to ensure efficient and safe GPU-side policy execution.
The key insight is that we distinguish \emph{warp-uniform} values (identical across warp threads, e.g., region identifiers) from \emph{lane-varying} values (thread-local GPU state). Policies may compute freely using lane-varying values, but these must not influence control-flow decisions or directly produce side effects visible outside a warp. To guarantee warp-level coherence, \sys mandates that branch conditions, loop bounds, and map-update keys be warp-uniform or derived via warp-level aggregation. Additionally, \sys prohibits GPU-wide barriers, global synchronization primitives, and non-uniform atomic operations, and imposes resource budgets per policy hook to bound memory and thread resource usage. These constraints ensure safe policy execution under GPU hardware semantics.

\subsubsection{Warp-level Execution Optimizations}

Even after SIMT verification, scalar per-thread eBPF execution still causes overhead (\eg duplicate map updates). To resolve this, \sys introduces a warp-level aggregated execution model, executing policy logic once per warp using a designated "warp leader" (typically lane 0). At each hook invocation, lanes first compute local contributions (e.g., addresses, counters) without influencing control flow or updating shared state. These contributions are then aggregated at warp granularity, and the warp leader executes the policy handler once using aggregated inputs, broadcasting the decision back to all lanes. \sys further employs compiler-level optimizations (specialization and inlining) tailored for warp-level execution.

\subsubsection{Hierarchical Cross-layer Maps for State Coordination}
\label{sec:cross-layer-maps}

To share state across asynchronous CPU and GPU contexts, \sys introduces cross-layer maps: Logically, each map is a unified key-value store accessible from host-side driver hooks, GPU-side device policies, and user-space control planes, verified through standard eBPF. Physically, maps are realized as hierarchical shards across host DRAM, GPU global memory, and GPU-local storage (e.g., shared memory, SM-local). The runtime dynamically determines shard placement based on access frequency, latency, and capacity constraints. Following eBPF's soft-state philosophy, \sys maps provide eventual consistency: the runtime periodically merges GPU-local map shards into canonical snapshots at GPU kernel completion boundaries. This snapshot-based model is sufficient because policy decisions rely on approximate statistics; occasional staleness affects optimality but cannot violate correctness invariants such as memory integrity, enforced by the GPU driver and hardware MMU.

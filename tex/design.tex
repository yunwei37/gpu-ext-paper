\noindent Cuprobe provides a dynamic, eBPF-based “uprobe/uretprobe” mechanism for GPU functions by attaching instrumentation at user‐land function entry and exit points. For example, the following eBPF program traces a tiled matrix‐multiply kernel (\texttt{matMulTiled}), incrementing a call counter and measuring total execution time:

    u32 pid = bpf_get_current_pid_tgid() >> 32;
    u64 ts  = bpf_ktime_get_ns();
    bpf_map_update_elem(&start_ts, &pid, &ts, BPF_ANY);
    u64 one = 1, *cnt = bpf_map_lookup_elem(&call_count, 
        &pid);  // increment call count
    if (cnt) *cnt += 1;
    else    bpf_map_update_elem(&call_count, &pid, &one,
        BPF_ANY);
}
SEC("curetprobe/_Z11matMulTiledPKfS0_Pf")
int curetprobe_matMulTiled(struct pt_regs *ctx) {
    u32 pid = bpf_get_current_pid_tgid() >> 32;
    u64 *tsp = bpf_map_lookup_elem(&start_ts, &pid);
    if (!tsp) return 0;
    u64 delta = bpf_ktime_get_ns() - *tsp;
    bpf_map_delete_elem(&start_ts, &pid);
    u64 *total = bpf_map_lookup_elem(&total_time_ns,
            &pid); // accumulate execution time
    if (total) {
        *total += delta;
        bpf_map_update_elem(&total_time_ns, &pid, 
            total, BPF_EXIST);
    } else {
        bpf_map_update_elem(&total_time_ns, &pid, 
            &delta, BPF_NOEXIST);
    }
}
\end{minted}

\noindent Curetprobe extends this model onto the GPU by translating these same eBPF probe handlers into PTX instrumentation snippets and injecting them directly into running CUDA kernels. At JIT time, \sys compiles the above eBPF bytecode into equivalent PTX trampolines at the entry and exit of \texttt{matMulTiled} within the GPU kernel image. These trampolines record per‐warp timestamps and update shared eBPF maps exactly as their CPU counterparts. By preserving the original map semantics, Curetprobe achieves function‐level profiling on the device without kernel reloads, delivering sub‐microsecond instrumentation overhead and live visibility into GPU execution.

This ensures that no instrumentation can stray into GPU-private buffers or access CPU memory outside the MPK-protected region. By keeping the kernel alive and dynamically swapping in new PTX probes, we eliminate repeated launches and enable truly live, on-the-fly GPU observability.

\subsection{GPU Trampoline}\label{sec:gpu_trampoline}

To support in‐place instrumentation without tearing down long‐running GPU kernels, \sys{} employs a lightweight PTX‐level ``trampoline” mechanism. 
A trampoline is a small stub of injected PTX code inserted at a designated patch point—typically at the entry or exit of a CUDA kernel function or at key memory‐access sites. 
When the GPU’s program counter reaches this stub, execution temporarily diverts into our instrumentation logic before resuming the original kernel flow.

Concretely, each trampoline stub performs three steps:
\begin{itemize}[leftmargin=*,itemsep=0pt]
  \item \textbf{Context Save:} Push the minimal set of live registers and predicate flags into a per‐warp scratch buffer in shared memory, preserving the kernel’s architectural state.
  \item \textbf{Instrumentation Jump:} Branch into the injected PTX snippet—compiled on the fly from eBPF bytecode—which may read or update shared eBPF maps, record timestamps, count events, or apply custom analysis.
  \item \textbf{Context Restore:} Reload the saved registers and flags, then jump back to the next instruction in the original kernel code.
\end{itemize}

By generating trampolines at JIT time and patching branch targets atomically, \sys{} ensures that no global kernel relaunch or module reload is required. Moreover, trampolines are confined within the \emph{protected domain} (see Section~\ref{sec:isolation}), so they may only access approved shared memory regions and may not overwrite application buffers. In our experiments, the added latency per trampoline invocation remains under 1 µs, enabling fine‐grained, live instrumentation of GPU kernels with negligible impact on overall throughput.

\subsection{Self‐Modifying Code}\label{sec:self_modifying_code}
We require true self-modifying PTX \xiangyu{What does true self-modifying PTX mean?} on the device to stream new instrumentation into a long-running kernel, but current NVIDIA drivers offer no direct support. 
To work around this, we piggy-back on ParallelGPU OS (POS)~\cite{huang2024parallelgpuos}, an OS-level framework that transparently checkpoints and restores GPU applications without any source changes. 
POS hooks every CUDA driver call to build a fine-grained DAG of kernel launches and their buffer read/write sets. 
By speculatively inferring each kernel’s buffer accesses from its arguments—and then validating those patterns at runtime—POS provides “soft” copy-on-write, dirty-bit, and on-demand-load semantics on hardware that lacks those primitives natively.

Building on POS’s buffering and dependency infrastructure, our runtime emits JIT-compiled PTX fragments and patches them directly into the resident kernel image. 
Whenever a new PTX snippet is injected, POS records the new code region in its DAG, applies soft copy-on-write to any overlapping buffer pages, and validates that the modified code and data views remain consistent before letting the kernel proceed.

This tight integration allows us to perform live code transformations—such as installing trampoline stubs or altering kernel logic—without restarting the GPU workload or risking state corruption. 
Thanks to POS’s dependency-driven scheduler and lightweight buffer-tracking, we achieve: (1) Transparent correctness: POS’s emulated COW and dirty-bit mechanisms isolate code patches and data updates, ensuring semantic integrity. 
(2) Concurrent operation: Checkpoint/restore tasks run in parallel with instrumentation injections, minimizing interruptions.

Overall, POS provides a robust substrate for on-the-fly PTX self-modification, enabling production-grade dynamic instrumentation of GPU kernels.

\subsection{Shared Memory}

We leverage \texttt{boost::managed\_shared\_memory} to create a unified buffer that both the host and device can access without expensive copies. 
This shared region holds critical data structures—eBPF maps, input batches, and intermediate states—mapped simultaneously into CPU and GPU address spaces. 
By ensuring GPU‐compatibility at allocation time, we eliminate the need to marshal or memcpy data between domains, yielding lower latency and reduced code complexity.

On such platforms, our \texttt{managed\_shared\_memory} can transparently scale to multi‐gigabyte working sets, with fine‐grained coherence handled by the interconnect fabric. 
This advancement will further minimize synchronization overhead and allow kernels to process broader data ranges without the usual replication or barrier penalties.

\subsection{Synchronization}
Given that multiple CPU threads and GPU kernels share data structures, synchronization must be carefully managed to avoid race conditions and ensure memory consistency. 
We rely on several mechanisms that operate at different levels. 
On the CPU side, standard lock-based or lock-free data structures (e.g., using \texttt{std::atomic} or Boost interprocess primitives) ensure that host processes do not introduce inconsistent states in shared regions. 
Within the GPU, we use CUDA atomic operations and device-wide memory fences to serialize updates to global or shared memory. 
This combined strategy, supported by a well-defined data layout in \texttt{managed\_shared\_memory}, ensures that asynchronous updates remain visible to all participants. 
For frequent small-scale synchronization events, we minimize warp-level conflicts by having only a small subset of threads perform atomic operations, whereas the rest of the kernel continues to process data in parallel.

\subsection{PTX Generation \& Injection}\label{sec:ptx_injection}

Our system performs eBPF or application-specific code transformations into PTX to enable GPU-side instrumentation and computation. 
When user-space or eBPF logic requests that certain functions be offloaded or traced on the GPU, our JIT compiler generates specialized PTX snippets. 
These are then dynamically injected into the running kernel through device-resident hooks. We refer to this technique as “PTX injection”, which allows us to intercept or insert instructions without tearing down the existing kernel context. 
This approach helps reduce overhead compared to stopping the kernel, recompiling the entire codebase, and relaunching it.

Once injected, the PTX code can interoperate with eBPF maps or other shared memory buffers, granting it direct access to the same data structures used by the CPU side. PTX injection creates a flexible environment for GPU instrumentation, tracepoints, and user-defined logic that can adapt in real time as new workloads arrive or instrumentation needs change. By carefully managing memory barriers and code patching points, we ensure that newly injected PTX interacts cleanly with the previously running kernel components.

\paragraph{Trampoline Mechanism}
To insert instrumentation at arbitrary points within a live kernel, \sys{} employs a PTX-level \emph{trampoline} mechanism. At runtime, we identify candidate patch points (e.g., function entry, memory-access sites, or barrier syncs) and emit a small trampoline stub in PTX that:
\begin{itemize}[leftmargin=*,itemsep=0pt]
  \item Saves the minimal GPU register and predicate state.
  \item Jumps into the injected instrumentation snippet.
  \item Restores the original state and resumes normal execution.
\end{itemize}
These trampolines are linked into the device’s code image via in-place patching of branch targets, enabling fine-grained hooking without requiring kernel relaunch or full recompilation. Our trampoline generator handles label resolution, register allocation, and insertion of necessary synchronization primitives to avoid hazards.



\subsection{Isolation Requirement}\label{sec:isolation}

Dynamic PTX injection and trampoline-based instrumentation introduce new code into live GPU kernels, which \xiangyu{must be prevented from --> might bring the risk of} corrupting application state or violating memory safety. 
To ensure that injected instrumentation runs in a strictly controlled environment, \sys{} enforces an \emph{isolation requirement} by placing all injected snippets into a protected execution domain.

\paragraph{Guardian-inspired GPU Partition}  
Drawing on the principles of Guardian’s PTX-level bounds checking for multi-tenant GPU sharing~\cite{pavlidakis2024guardian}, \sys{} partitions the GPU address space at runtime and instruments every load/store with lightweight fencing logic:

\begin{itemize}[leftmargin=*,itemsep=0pt]
  \item \textbf{Dynamic Partitioning:} At initialization, \sys{} uses one partition of entire GPU memory. Each instrumentation snippet is tagged with its owner’s partition ID.
  \item \textbf{PTX-Level Bounds Fencing:} Before every memory access, bitwise AND/OR operations mask the computed address into the tenant’s partition range, guaranteeing that out-of-bounds addresses wrap harmlessly within the correct domain.
  \item \textbf{Client–Server Enforcement:} Inspired by Guardian’s client–server model, all CUDA calls (allocations, copies, launches) are intercepted and forwarded to a trusted Manager. This server maintains the partition bounds table and rejects any operation that would violate domain isolation.
\end{itemize}

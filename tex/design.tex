\section{\sys Design}

% \arq{Introduce \sys following the intro discussion}

This section presents the design of \sys{}, a programmable OS subsystem for safe, dynamic, full-stack GPU resource management. We describe the system workflow (\S\ref{sec:workflow}), resource state machines (\S\ref{sec:design-interfaces}), GPU-specific eBPF challenges (\S\ref{sec:motivation-challenges}), and our asynchronous execution model (\S\ref{sec:exec-model}).

\subsection{\sys{} Workflow}
\label{sec:workflow}

\sys{} extends eBPF (extended Berkeley Packet Filter) to GPU resource management. eBPF programs are callbacks attached to hooks such as \texttt{struct\_ops}, \texttt{kprobe}, and \texttt{uprobe}, using load-time verification and JIT compilation for OS-kernel execution. The Linux verifier checks termination, memory safety, types, and calls to approved helpers and kfuncs (OS kernel functions). As shown in Figure~\ref{fig:system-design}, \sys{} extends the execution pipeline to GPUs: policies contain host and device components, are JIT-compiled to CPU or GPU code (e.g., PTX), exchange state through cross-layer maps, and are installed through OS kernel hooks and DBI. The device-verification prototype adds SIMT checks; its enforcement and deployment boundaries are stated in \S\ref{sec:verification}.

\subsection{Resource State Machines}
\label{sec:design-interfaces}

\sys{} defines three resource domains. Memory chunks move between host and device memory via eviction and prefetching. GPU kernels (launched tasks) and GPU thread-blocks (parallel execution units within kernels) transition among ready, running, and finished states through scheduling and preemption operations.

\subsection{GPU-Specific Challenges for eBPF Extensibility}
\label{sec:motivation-challenges}
% \arq{If we're tight on space, I think this can become a paragraph in 3.0 instead of being a subsection.}

CPU eBPF does not directly transfer to GPUs. CPU eBPF callbacks make synchronous decisions at fixed transition points, immediately affecting local resources, and subsystems are extended independently. In contrast, GPUs are discrete processors: host policy decisions affect resources asynchronously on a separate device. Thus, three architectural mismatches introduce key challenges:

\textbf{Cross-device latency.} CPU eBPF callbacks execute synchronously, but GPU operations (e.g., page migration across PCIe) take milliseconds (\S\ref{sec:arch-gpu}). GPU policies must proactively initiate asynchronous actions instead of reacting only at faults.

\textbf{Memory-scheduling coupling.} CPU extensibility treats scheduling and memory independently, but GPU page faults simultaneously trigger memory events and scheduling stalls due to limited device memory. GPU policies must jointly coordinate these domains.

\textbf{OS kernel bypass.} GPU runtimes bypass the OS kernel (e.g., user-space command buffers, doorbells), revealing only coarse-grained resource events to drivers, not fine-grained GPU kernel launches or application phases. GPU policies must attach to user-space application functions, yet standard eBPF prohibits these callbacks from modifying OS state required for resource management. Exposing GPU driver controls without addressing these mismatches risks resource leaks, hardware hangs, or OS kernel panics.

\subsection{Asynchronous Execution Model}
\label{sec:exec-model}

To address these challenges, \sys{} separates callback triggers from their effects (\Cref{fig:exec-model}). Driver hooks, user-space uprobes, and device-side observations supply policy events; eBPF workqueues can defer host-side handling to an appropriate execution context. A policy can coordinate memory and scheduling requests, but each request must use an actuator with the required locking and object-lifetime contract. Preempting a tenant changes execution order; it does not itself release that tenant's GPU memory. The validated interfaces and their current limits are described below.

The policy interface exposes two dimensions: \emph{selection} (choosing resources, e.g., eviction order or tenant priority) and \emph{timing} (when to request an operation). The driver owns resource allocation, lifetime, and actuation. Typed requests are validated before the covered resource mutations; rejection either preserves the prior state, invokes native behavior, or returns an error according to that operation's contract (\S\ref{sec:verification}). Currently, a single policy program is loaded system-wide but may internally differentiate tenant treatment for priorities, similar to sched\_ext; per-tenant isolation is future work.

\subsubsection{Warp-level Execution Optimizations}

Scalar per-thread eBPF execution can duplicate policy work and map updates. Warp-level aggregated execution instead combines lane-local observations, executes a scalar handler in a warp leader, and broadcasts its decisions (\S\ref{sec:implementation}). This optimization is distinct from verifier enforcement: executing once per warp does not by itself establish that a program satisfies the SIMT checks.


\subsubsection{Hierarchical Cross-layer Maps for State Coordination}
\label{sec:cross-layer-maps}

Cross-layer maps exchange observations between host driver hooks, GPU-side policies, and user-space control planes. Device-local shards reduce access costs, while host-visible summaries support cross-domain decisions (\S\ref{sec:implementation}). Delayed publication makes these observations potentially stale. Approximate access statistics can guide a policy, but they do not replace driver-owned identity, membership, and range checks before a covered transition. Nor does eventual consistency guarantee freedom from thrashing or unfair decisions.

\subsection{Example: MoE Expert Offloading}

% \arq{I think this would be a good final subsection that "summarizes" most of what we just read}
We illustrate this model using Mixture-of-Experts (MoE) offloading, where models exceed GPU memory capacity. Since all experts do not fit and activate concurrently, the GPU driver continuously evicts and migrates pages. The default driver's LRU eviction and prefetching are unaware of expert activations, causing costly PCIe DMA stalls.

The conceptual policy in \Cref{fig:moe-listing} combines three eBPF components through shared observations: device-side access counting, application-triggered prefetch requests (\emph{timing}), and driver-side cold-page eviction ordering (\emph{selection}). The intended overlap is between memory migration and computation, while scheduling requests can change which tenant executes. Page-granularity selection differs from framework-level expert-atomic offloading. The listing uses illustrative legacy helper names, not the current validated ABI: raw list mutations have been replaced by typed requests, and arbitrary deferred migration still requires an object-lifetime-safe interface.
Each eBPF program captures partial state at different layers; cross-layer maps unify this fragmented visibility to orchestrate state transitions across host and GPU.

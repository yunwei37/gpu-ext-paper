\sys{} is a programmable OS subsystem that extends eBPF (extended Berkeley Packet Filter) to provide safe, dynamic, and full-stack GPU resource management. eBPF programs are callbacks attached to hook points such as \texttt{struct\_ops}, \texttt{kprobe}, and \texttt{uprobe}, allowing user-supplied programs to run safely inside the OS kernel: programs are verified at load time, then JIT-compiled to native code. The verifier guarantees termination, memory safety, type correctness, and that programs call only approved helpers and kfuncs (OS kernel functions). As shown in Figure~\ref{fig:system-design}, \sys{} extends this pipeline to GPUs: policy authors use the standard eBPF toolchain to build and load policies containing both host and device parts. The runtime spans host driver and GPU device, verifies policies with SIMT-aware checks for device-side programs (\S\ref{sec:verification}), only allows changing transition timing and order to ensure safety, JIT-compiles them to native CPU code or GPU instructions (e.g., PTX), places maps hierarchically, and uses kernel hooks and DBI tools to dynamically install policies without application or driver restarts.

\subsection{GPU-Specific Challenges for eBPF Extensibility}
\label{sec:motivation-challenges}
\arq{If we're tight on space, I think this can become a paragraph in 3.0 instead of being a subsection.}

However, the CPU eBPF model does not directly transfer to GPUs. In CPU eBPF systems, each eBPF callback makes a single synchronous decision at a fixed transition point, with effects immediately taking place on local resources, and each subsystem is extended independently. The GPU is a discrete processor with its own execution model and resources, and policy decisions made in the host take effect on a separate device. Three mismatches between the CPU model and GPU architecture create challenges beyond the lack of safe programmable extension in GPU drivers:

\textbf{Cross-device latency.} CPU eBPF callbacks execute synchronously, but GPU operations such as page migration cross the PCIe boundary and take milliseconds (\S\ref{sec:arch-gpu}). Policies must initiate transitions asynchronously and act proactively, not only reactively at the fault.

\textbf{Memory-scheduling coupling.} CPU extensibility treats scheduling and memory as independent subsystems (\texttt{sched\_ext} and \texttt{cache\_ext}), but on GPU, limited device memory tightly couples these domains, as a page fault is simultaneously a memory event and a scheduling stall. GPU policies must coordinate across both.

\textbf{OS kernel bypass.} CPU eBPF runs on the same processor it manages, but GPU runtimes bypass the OS kernel for work submission (e.g., user-space command buffers and doorbells), so the driver sees only coarse resource events, not individual GPU kernel launches or application phase transitions (e.g., LLM prefill-to-decode, FAISS build-to-search). Policies must attach to user-space and device-side triggers, yet traditional eBPF does not allow such callbacks to modify OS state required to implement resource management policies.
Naively exposing low-level GPU driver controls without addressing these mismatches risks resource leaks, hardware hangs, or OS kernel panics.

\subsubsection{Programmable State Transitions}

To address these challenges, \sys{} decouples policy triggers from their effects, modeling GPU resource management as programmable, asynchronous transitions on resource state machines. Policies are eBPF programs that direct state transitions through verified OS kernel functions (\emph{kfuncs}), and attach to diverse trigger points, including driver callbacks, application functions (uprobes), device-side execution events, and schedule tasks (\texttt{bpf\_wq}). Each trigger can initiate multiple state transitions asynchronously across memory and scheduling domains: i.e., without blocking on completion, proactively before faults occur, and on deferred schedules. For example, a uprobe at \texttt{cudaLaunchKernel} can asynchronously initiate a 6.6\,ms DMA prefetch informed by device-side observations while concurrently preempting another tenant's context to free GPU memory.

\sys defines three resource domains. Memory chunks transition between on-host and on-device through policy-reordered eviction and prefetch. Both GPU kernel and GPU thread-block level compute contexts transition between ready, running and completed, with preemption at per-GPU-kernel granularity. Device-side eBPF captures fine-grained runtime state and coordinates with host-side policies via shared cross-layer maps (\S\ref{sec:impl-host}).

To ensure OS kernel safety, verified kfuncs constrain state transitions to two dimensions: \emph{selection} (which resource to transition, e.g., evict chunk A before B, preempt tenant X for Y) and \emph{timing} (when to initiate, e.g., prefetch proactively rather than waiting for a fault), and the state machine is always managed by the driver mechanism. In multi-tenant settings, a single administrator-defined policy governs all tenants, as with sched\_ext; per-tenant policy isolation is future work.

A \sys{} policy uses three cooperating eBPF programs at different layers (\Cref{fig:moe-listing}), coordinating via a shared cross-layer map. First, during GPU kernel execution, a device-side eBPF handler inserted at warp entry tracks warp-level accesses to expert pages, recording per-page access counts for each warp in a hierarchical cross-layer map. Second, a uprobe eBPF program attached to \texttt{cuda\-Launch\-Kernel} proactively reads these counts to predict upcoming expert activations and asynchronously initiates cross-device prefetches (\texttt{bpf\_gpu\_\allowbreak{}prefetch\_async}), overlapping the millisecond-scale memory migration with computation to avoid expensive stalls (\emph{timing}). If memory pressure arises, this same program coordinates across memory and scheduling by preempting lower-priority GPU tasks via \texttt{gdrv\_sched\_\allowbreak{}preempt} (\emph{selection}). Finally, upon memory eviction (\emph{evict\_prepare}), a driver-side eBPF handler leverages the same expert access counts to evict cold pages first (LFU ordering), protecting hot experts (\emph{selection}). Unlike framework-level offloading that often migrates experts as atomic units, \sys{} operates at page granularity, enabling finer-grained compute-transfer overlap.
Each eBPF program exists because policy-relevant state is split across layers; cross-layer maps bridge this fragmented visibility to orchestrate state transitions across GPU and host boundaries.

\subsection{Runtime Verification and Optimizations}
\label{sec:verification}

\sys policies execute directly within privileged GPU driver and OS kernel contexts, making safety guarantees critical. The threat model follows standard eBPF: administrators are trusted, but policy code may be buggy or misconfigured. The trusted computing base (TCB) includes the OS kernel, \sys driver module, GPU compiler backend, and GPU driver/firmware. Host-side verification reuses the Linux eBPF verifier unchanged; \sys-specific kfuncs are declared via BTF metadata.

\subsubsection{SIMT-aware Verification}

Because the GPU executes in SIMT (Single Instruction, Multiple Threads) mode, device-side eBPF programs must respect warp-level execution semantics, while preserving eBPF's scalar programming model to pass the verifier. \sys introduces a SIMT-aware verification model enforcing warp-level uniformity constraints to ensure efficiency and safety.
The key insight is that we distinguish \emph{warp-uniform} values (identical across warp threads, e.g., region identifiers) from \emph{lane-varying} values (thread-local GPU state). Policies may compute freely using lane-varying values, but these must not influence control-flow decisions or directly produce side effects visible outside a warp. To guarantee warp-level coherence, \sys mandates that branch conditions, loop bounds, and map-update keys be warp-uniform or derived via warp-level aggregation. Additionally, \sys prohibits GPU-wide barriers, global synchronization primitives, and non-uniform atomic operations, and imposes resource budgets per policy hook to bound memory and thread resource usage. These constraints ensure safe policy execution under GPU hardware semantics.

\subsubsection{Warp-level Execution Optimizations}

Even after SIMT verification, scalar per-thread eBPF execution still causes overhead (\eg duplicate map updates). To resolve this, \sys introduces a warp-level aggregated execution model, executing policy logic once per warp using a designated "warp leader" (typically lane 0). At each hook invocation, lanes first compute local contributions (e.g., addresses, counters) without influencing control flow or updating shared state. These contributions are then aggregated at warp granularity, and the warp leader executes the policy handler once using aggregated inputs, broadcasting the decision back to all lanes. \sys further employs compiler-level optimizations (specialization and inlining) tailored for warp-level execution.

\subsubsection{Hierarchical Cross-layer Maps for State Coordination}
\label{sec:cross-layer-maps}

To share state across asynchronous CPU and GPU contexts, \sys introduces cross-layer maps: Logically, each map is a unified key-value store accessible from host-side driver hooks, GPU-side device policies, and user-space control planes, so it can be verified through standard eBPF. Physically, maps are realized as hierarchical shards across host DRAM, GPU global memory, and GPU-local storage (e.g., shared memory, SM-local). The runtime dynamically determines shard placement based on access frequency, latency, and capacity constraints. Following eBPF's soft-state philosophy, \sys maps provide eventual consistency: the runtime periodically merges GPU-local map shards into canonical snapshots at GPU kernel-completion boundaries. This snapshot-based model is sufficient because policy decisions rely on approximate statistics; occasional staleness affects optimality but cannot violate correctness invariants such as memory integrity, enforced by the GPU driver and hardware MMU.

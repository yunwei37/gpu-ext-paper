\section{Portability}
\label{sec:discussion}

\sys is designed with portability in mind, though our current implementation and evaluation specifically target NVIDIA's GPU stack due to its broad deployment in production. We note that NVIDIA's production drivers largely bypass Linux’s standard kernel interfaces, making immediate portability challenging. On the host side, our design aligns conceptually with generic Linux abstractions: for memory management, we align with Linux's Heterogeneous Memory Management (HMM) and its \texttt{migrate\_vma} interface—already adopted by other vendors such as AMD ROCm with XNACK retryable faults; for scheduling, we abstract GPU queues following the Linux DRM scheduler’s \texttt{drm\_sched\_entity} model, mapping directly to NVIDIA's TSGs and potentially AMD's user-mode queues, whose scheduling parameters (e.g., \texttt{HWS}, \texttt{HWS\_NO\_OVERSUBSCRIPTION}) are enforced by vendor firmware during HQD mapping~\cite{rocm-gpu-memory,linux-gpusvm-doc,drm-gpu-sched,amdgpu-userq-doc}. On the device side, our compiler generates eBPF bytecode targeting the vendor-neutral SPIR-V representation, enabling future support for generic compute runtimes such as AMD ROCm and Intel Level Zero. However, end-to-end portability is not yet realized, as it fundamentally depends on vendor-specific runtime support, instrumentation hooks, and hardware-specific performance tuning. Addressing these vendor-specific challenges remains future work~\cite{spirv-ir-rfc,llvm-offload-design}.

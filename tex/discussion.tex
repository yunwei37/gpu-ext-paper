\section{Portability Discussion}
\label{sec:discussion}

Our prototype targets NVIDIA GPUs via UVM and the open GPU kernel modules, but the design of \sys is intentionally vendor-agnostic along all three axes it touches: memory management, scheduling, and device offload. On AMD, the analogue of CUDA UVM/UVA is ROCm/HIP unified or managed memory, where \texttt{hipMallocManaged}, \texttt{hipMemAdvise}, and \texttt{hipMemPrefetchAsync} allocate a single system-wide virtual address space and rely on Linux Heterogeneous Memory Management (HMM) plus XNACK-style retryable GPU page faults to migrate and cache pages between host DDR and GPU VRAM~\cite{rocm-gpu-memory,gpu-memory,amd-node-memory-model}. In the kernel, HMM and the AMD KFD SVM layer maintain per-process shared-virtual-memory ranges over CPU virtual address intervals and use generic \texttt{hmm\_mirror}/\texttt{hmm\_range} snapshots plus \texttt{migrate\_vma()} and device-private memory to move pages and bind them into GPU page tables, while the newer DRM GPU-SVM framework factors these mechanisms into a vendor-neutral \texttt{drm\_gpusvm\_range} abstraction~\cite{kuehling-kfd-svm,linux-gpusvm-doc}. At the scheduling layer, modern Linux GPU drivers—including amdgpu—share the DRM GPU scheduler, where jobs are submitted through per-context \texttt{drm\_sched\_entity} queues into hardware run queues and scheduled according to pluggable policies (FIFO, fair, deadline-aware) via driver-provided backend callbacks for job submission, timeouts, and preemption~\cite{drm-gpu-sched,deshmukh-gsoc-sched}. AMD’s compute stack further exposes user-mode queues through KFD and the ROCm DBG API: applications enqueue AQL packets into user-space queues, which are multiplexed onto a limited number of hardware queues by firmware and the kernel driver, with support for oversubscription and priority between tenants~\cite{amdgpu-userq-doc,rocm-dbgapi,amd-oversubscription}. These abstractions align closely with \sys's host-side \emph{Submit/Admit/Preempt/Complete} hooks and device-side block scheduler: on AMD, the same eBPF policies can attach at DRM scheduler and KFD queue-management callbacks instead of NVIDIA UVM/scheduler hooks, while retaining a unified view of regions, tenants, and priorities in shared BPF maps. On the device side, our prototype lowers verified eBPF IR to PTX, but LLVM already provides a production AMDGPU backend and generic offload machinery, and ongoing work on SPIR-V as a vendor-agnostic GPU IR makes it feasible to target AMD (and other vendors) by swapping the eBPF$\rightarrow$PTX backend for an eBPF$\rightarrow$AMDGPU or eBPF$\rightarrow$SPIR-V backend and adapting trampolines to each ISA’s wavefront/warp model; the verifier, control plane, and policy code remain unchanged~\cite{llvm-amdgpu-backend,llvm-offload-design,spirv-ir-rfc}.

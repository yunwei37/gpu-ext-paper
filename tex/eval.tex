\section{Evaluation}
\label{sec:eval}

Our evaluation addresses the following research questions:

\begin{itemize}[leftmargin=*]
  \item \textbf{RQ1 (Single-Tenant Management):} How much performance gain can \sys's programmable memory and scheduling policies provide on oversubscribed single-tenant workloads?
  \item \textbf{RQ2 (Agent-Driven Exploration):} Does \sys's eBPF containment model make GPU policy space exploration safe and productive for AI agents?
  \item \textbf{RQ3 (Multi-Tenant Management):} Does \sys improve tail latency, throughput, and resource fairness compared to user-space and global policies in multi-tenant settings? 
  \item \textbf{RQ4 (Overhead):} What is the overhead of \sys{}'s core mechanisms and observability capabilities? 
\end{itemize}


\subsection{Methodology and Setup}

We evaluate \sys on two machines: Server~A with Intel Core Ultra~9 285K (24 cores), 128~GB DDR5 RAM, and NVIDIA RTX~5090 GPU; Server~B with dual Intel Gold 6138 (80 cores), 256~GB RAM, and NVIDIA P40 GPU. Unless otherwise specified, the original case studies run on Server~A and report geometric means of 10 trials; the historical single-round comparison and new paired studies state their different sampling and aggregation explicitly. We compare \sys{} against three classes of baselines: (1) driver defaults (UVM LRU/FIFO eviction, native GPU scheduler), (2) application-level hints (\texttt{cudaMemAdvise}), and (3) framework-managed policies (e.g., llama.cpp \texttt{ncmoe}, vLLM CPU offload, LMCache) where applicable. The original application case studies use PyTorch (version 2.9.0) and vLLM (version 0.11.0) with custom allocators, llama.cpp (version 7101), and Faiss (version 1.13.0) with UVM build config. Their driver policies do not require application-source changes beyond the stated UVM setup; the matched component ports in \S\ref{sec:policy-mechanism} use explicit framework and compatibility adapters.

\subsection{RQ1: Single-Tenant Memory and Scheduling Policies on GPU kernels}

\paragraph{Memory Prefetch Policies}
We evaluate host-device prefetch coordination using a vector-add GPU kernel~\cite{nvidia_cuda_samples} with stride access pattern and 40GB working set (1.25$\times$ oversubscription). Device-side L2 prefetch instructions (\texttt{prefetch.\allowbreak{}global.\allowbreak{}L2}) trigger non-blocking page faults, while host-side callbacks extend prefetching to additional pages. As shown in \Cref{fig:clc-policies}a, device-only prefetch (45~LOC) at thread entry achieves 1.34$\times$ speedup while combined host-device stride-based eBPF prefetch (472~LOC host + 45~LOC device) achieves 1.77$\times$. However, sequential prefetch (573~LOC) degrades performance by 8\% due to pattern mismatch.

\paragraph{Single-Tenant Block Scheduler}
We apply a \sys-based thread block scheduler to workloads with load imbalance. Using cluster-style launch where persistent worker blocks pull work units via \texttt{should\_\allowbreak{}try\_steal}, we evaluate three policies: FixedWork (static block assignment, no scheduler), Greedy (always-steal, 16~LOC), and LatencyBudget (workload-aware with per-block time limits, 19~LOC).
\Cref{fig:clc-policies}b compares these policies across two GEMM workloads. Under moderate imbalance, both Greedy and LatencyBudget reduce latency by $\sim$11\%. Under heavy-tail workloads where 10\% of blocks perform 100--200$\times$ more work, Greedy increases latency by 20\% due to contention on heavy blocks. LatencyBudget, which caps per-block stealing time, matches fixed-work baseline. This highlights \sys's programmability: different workloads require different scheduling strategies.

\subsection{RQ2: Agent-Driven Policy Exploration Case Studies}

We provided an AI coding agent (Claude Code with Opus 4.5) with \sys{}'s eBPF interfaces; humans authored the initial framework and benchmark harness. Retained study summaries report 59 generated policies, 974 benchmark runs and 244 code edits over 20 days, consuming 5.5M tokens (\$388 API cost); approximately 75\% of explored policies yielded negative results. Original interaction logs are not fully available, so these summaries are not independently replayable transcript evidence. The retained 50-event taxonomy contains 24 logic bugs, 18 performance regressions, 2 verifier rejections, 2 GPU Xid faults, 2 system hangs, one build failure and one driver bug. Repository-source reconciliation supports 46 entries fully and four partially. No OS kernel panic or data corruption is documented, but the records include system OOM requiring hard reboots: absence of a recorded kernel panic is not proof of fault-free execution or recovery without restarts. GPU faults are not verifier rejections. We next describe four performance case studies; verification and transition-validation boundaries are given in \S\ref{sec:verification}.

\paragraph{Expert Offloading (llama.cpp GPT-OSS-120B)}
We evaluate \sys on GPT-OSS-120B MXFP4 MoE (59~GB) in llama.cpp on RTX 5090 (32~GB), requiring 1.84$\times$ oversubscription. We compare five configurations: framework-managed CPU offloading (\texttt{ncmoe=\allowbreak{}32/64}), default UVM, UVM with application-level hints (\texttt{cuda\-Mem\-Advise}), and \sys with eBPF-based host-device prefetching (\S\ref{sec:design-interfaces}).

\paragraph{KV-cache Offloading (vLLM Qwen-30B MoE)}
We evaluate \sys on the Qwen-30B FP8 MoE model ($\approx$30GB) on RTX 5090 (32GB). The model nearly fills GPU VRAM, so the default no-offload configuration OOMs under load. We stress KV-cache growth by sending 100 concurrent requests from ShareGPT~\cite{sharegpt} (single-round, no prefix caching), resulting in 36--40GB total footprint ($\approx$60K tokens KV-cache). Existing solutions offload KV-cache or experts but not both; UVM attempts on-demand migration of both, leading to thrashing.
We compare vLLM's CPU-offload mode (\texttt{--cpu-offload-gb 8}) against \sys with UVM and a sequential prefetch policy. \sys improves mean and p99 time-to-first-token by 1.7--2$\times$ and decoding throughput by 1.3$\times$ over vLLM's default framework-managed offload (\Cref{fig:vllm-kv-offload}), matching LMCache~\cite{lmcache}, a state-of-the-art KV-cache offloading framework. Notably, UVM without \sys policies performs worse than vLLM's offload, while \sys performs similarly to the best framework offloading, with better tail latency, dynamically and transparently.

Uniform sequential prefetch thrashed KV-cache and weight pages. Device tracing led to region-specific prefetch---sequential for temporally/per-request-local KV state and stride for weights---with PCIe-guided aggressiveness (573~LOC) and LFU eviction (304~LOC; $\sim$880 total), retaining hot pages and avoiding the uniform policy's thrashing.

\paragraph{Graph Neural Networks (GNN Training)}
We evaluate \sys on PyTorch-based GCN training with random graphs of varying sizes (1M--15M nodes, 10 edges/node). \Cref{fig:gnn-epoch} shows epoch time across five configurations: native GPU allocation (no UVM), UVM with and without user-space prefetching (\texttt{cudaMemPrefetchAsync}), and each UVM configuration with \sys eBPF-based optimization.
With UVM enabled via a custom allocator, each epoch allocates memory on CPU and migrates to GPU on demand, incurring overhead. Developers can pre-migrate pages via \texttt{cudaMemPrefetchAsync}, achieving 5.5$\times$ speedup at moderate oversubscription, but this requires application modification. Without user hints, eBPF optimizes page fault handling via aggressive prefetching, achieving 2.65$\times$ speedup transparently. With both user-expressed prefetching and \sys, it achieves 1.44$\times$ additional speedup by prefetching larger regions and reducing blocking faults.
Native GPU allocation (no UVM) achieves the highest performance when data fits in memory (1.89~s at 5M nodes) but fails with OOM beyond $\sim$8M nodes. UVM with \sys prefetching enables training at 15M nodes (2.17$\times$ oversubscription) with near-native performance and no further application-source changes beyond the stated custom allocator.

Allocation uprobes and device history drive 573~LOC sequential prefetch. K=1 cut epoch time 21\%; K=2/3 lost 16\%, and adaptive K up to 6 lost 46\%. The agent identified PCIe saturation, rather than lock contention, as the bottleneck.

\paragraph{Faiss Vector Search}
We evaluate \sys on vector similarity search using the SIFT dataset with an IVF4096,Flat index, scaling from 20M (9.5GB) to 50M (24GB) and 100M (48GB, exceeding GPU memory). IVF indexes have a two-level structure: frequently-accessed centroids and larger posting lists, and Faiss operations have two distinct phases: BUILD performs sequential scans while SEARCH issues random accesses.
\sys reduces build time by 21--29\% on 50M, scaling to 27--40\% on 100M as memory pressure grows. For search workloads, \sys reduces latency by 10--16\% across different \texttt{nprobe} settings despite the random access patterns inherent in ANN search. As shown in \Cref{fig:faiss-perf}, the converged policy ($\sim$1090~LOC: sequential prefetch 573~LOC + stride prefetch 472~LOC + device-side 45~LOC) prefetches posting lists sequentially for oversubscribed datasets and uses stride prediction for K-means iterations during index construction; device-side eBPF programs also trigger prefetching of corresponding posting lists.

Only 2/8 policies across five iterations improved performance. Phase detection with cycle eviction helped BUILD but hurt SEARCH; forward-drifting queries confused the classifier. Correcting it favored default eviction. Version three converged; a later fast-path bug froze SEARCH and was fixed in one iteration.

\paragraph{Memory-bound Priority Differentiation}
The historical memory-priority comparison uses HotSpot~\cite{che2009rodinia}, GEMM from PolyBench~\cite{grauer2012auto}, and K-Means~\cite{gu2020uvmbench}, with two concurrent processes under UVM oversubscription. Labels use priority values 0--100 (lower = higher priority): \texttt{Prefetch(lo,hi)} selects prefetch recipients (454~LOC), and \texttt{Evict(lo,hi)} selects eviction treatment (472~LOC). References are no-policy execution, isolated single-process time, and twice that time as a sequential reference, not a theoretical lower bound.

\Cref{fig:all-kernels-priority} retains the complete single-round observations: selected memory policies reduce the recorded pair-completion proxy by 55--92\% relative to their memory-file baselines. These are not repeated estimates. The separate scheduler runs did not retain successful attachment or policy-hit evidence, and their initialization-only policy was started after the workloads. Their small observed differences therefore cannot establish that an engaged scheduling policy is ineffective. Sequential process waits also prevent recovery of independent per-tenant finish times from those rows. This comparison motivates, but does not isolate, the choice of memory versus scheduling policy; the same-policy UVM cost experiment and new scheduling comparisons answer narrower controlled questions in \S\ref{sec:policy-mechanism}.

\paragraph{Two-Tenant: High-Priority LLM Inference + Background Training}
We run two tenants sharing a single GPU: T1 is a high-priority \texttt{llama.cpp} inference service (LC workload) serving 100 ShareGPT prompts at 0.2 RPS, and T2 is a background PyTorch GNN training job (BE workload) with 8M nodes requiring 36GB peak memory (oversubscribed). We compare default UVM (driver FIFO/LRU) against \sys per-tenant memory and scheduler policies (1334~LOC, combining Quota LRU, Tree-based Prefetch, and Dynamic Timeslice). \Cref{fig:two-tenant} shows mutual improvement: LC TPOT drops by 40--45\% and TTFT by 14--20\%, while GNN training simultaneously improves by 28\%, approaching the ideal fair share baseline. This shows \sys reduces contention for both workloads rather than favoring one over the other.

\paragraph{Device-side Overhead}
We evaluate device-side observability tools built on \sys (\Cref{tab:obs-overhead}) on NVIDIA P40 GPU using llama.cpp prefill (Llama 1B, sequence-mixed). Tools include \texttt{kernel\-ret\-snoop} (per-block finish timestamps), \texttt{thread\-hist} (load imbalance detection), and \texttt{launch\-late} (GPU kernel launch latency). Overhead is measured as token/s degradation during prefill. \sys achieves 3--14\% overhead versus NVBit's 85--93\%~\cite{villa2019nvbit}, due to the warp-uniform execution model. Attaching to a running process takes 273\,ms on average from \texttt{bpftime trace} startup to first GPU kernel detection, without application restart.

\paragraph{Device-side Runtime Optimization}
We evaluate device-side \sys mechanisms using a vector-add CUDA GPU kernel (32 elements, 10K iterations) from cuda-sample~\cite{nvidia_cuda_samples} on RTX 5090. \Cref{fig:microbench}(a) compares \sys's SIMT-aware warp-level execution against eGPU~\cite{egpu} that injects eBPF bytecode without SIMT-specific verification and optimizations. The baseline incurs overhead due to per-thread execution and uncoalesced memory access, while \sys's warp-uniform execution and coalesced map access reduce overhead by 60--80\%. \Cref{fig:microbench}(b) shows CPU map access via PCIe is 6000$\times$ slower than GPU-side operations, motivating \sys's hierarchical map design that keeps hot state on GPU.

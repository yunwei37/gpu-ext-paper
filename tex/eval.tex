
\section{Evaluation}
\label{sec:evaluation}

We evaluated \sys{} on three machines. Server A is a dual-socket Intel Gold 6138 processor (80 cores, 2.0 GHz, 55 MB LLC) equipped with 256 GB DDR3 RAM and an NVIDIA P40 GPU. Server B is a single socket Intel Xeon 6787p (86 cores, 2.0 GHz, 336MB LLC) with 768 GB DDR5 RAM(512GB CXL Module) and an NVIDIA H100 GPU. Server C is a Grace Hopper Machine. Unless otherwise mentioned, each metric is the average of 10 trials on server A.  We report averages using geometric mean when that is appropriate (\eg when calculating an average speedup).



\subsection{Micro-benchmark Performance}

We quantify instrumentation overhead with a latency micro-benchmark that measures GPU load/store latency under \sys{} vs. NVBit (gpumemtrace~\cite{villa2019nvbit}) across varying access sizes. As shown in Figure~\ref{fig:end_to_end_latency}, \sys{} adds substantially less latency than NVBit, staying low and stable below 128 KB and rising modestly thereafter. \Cref{fig:latency1} compares with the PyTorch profiler (CUPTI+NVTX): p10 and mean latencies are slightly better under \sys{}. Lightweight PTX injection at runtime is the key enabler of the lower overhead.

\subsection{\sys{} Performance}
We compare end-to-end throughput and time-to-result against a native baseline (no persistent kernel, no PTX injection). For small batches, \sys{} pays modest startup/JIT cost but reduces launch frequency; for larger or irregular workloads, it matches or beats native by avoiding relaunches and sustaining higher utilization.

\subsection{Shared Memory Performance}
We benchmark shared-memory bandwidth and one-way latency on three servers using a 1 GiB region and both CPU-only and GPU access patterns (GPU-to-CPU and CPU-to-GPU). Servers A/B deliver 12–18 GB/s over PCIe with 8–15 µs cross-domain latencies; Server C's coherent fabric sustains \(>100\) GB/s and \(<500\) ns round-trip, highlighting the advantage of hardware coherence for live instrumentation.

\subsection{Use Case Evaluation}\label{sec:usecase_evaluation}

\subsubsection{General GPU Observability Tools}\label{sec:eval_observability}
We evaluate the suite of bcc-style observability tools across diverse workloads, measuring accuracy, overhead, and practical utility.

\paragraph{kernelretsnoop - Thread Divergence Detection}
We apply kernelretsnoop to a matrix multiply kernel with conditional boundary checks. The tool reveals that threads handling edge cases (5\% of total threads) exhibit 600-850ns longer execution times compared to interior threads. Per-thread timestamp accuracy is within 10ns of hardware performance counters. Overhead for timestamping all threads is 2.1\% on average. Armed with this insight, we refactor boundary handling to eliminate divergence, improving overall kernel performance by 8\%.

\paragraph{threadhist - Workload Balance Analysis}
Running threadhist on a particle simulation with 1M particles across 256 thread blocks reveals significant imbalance: blocks processing dense regions execute 2.3× more iterations than sparse-region blocks. The histogram shows a bimodal distribution with peaks at 4K and 9K executions per thread. Redistributing particles based on spatial density (guided by threadhist data) reduces execution variance to 15\% and improves overall throughput by 18\%. Tool overhead is 1.8\% due to atomic increments on per-thread counters.

\paragraph{launchlate - Launch Latency Profiling}
We measure launch latency across a pipeline of 50 small kernels (each 100 \(\mu\)s execution time). Default synchronous execution shows high variance in launch latency (150-550 \(\mu\)s per kernel) due to queue dependencies. Total pipeline time is 32ms (50 kernels × 100 \(\mu\)s + 50 launches × 440 \(\mu\)s average). After identifying this bottleneck with launchlate, we switch to CUDA graphs for batched launches, reducing total time to 7.2ms (5ms kernel execution + 2.2ms graph launch overhead). The tool adds negligible overhead (<0.5\%) as it only measures at kernel boundaries.

\paragraph{mem\_trace - Memory Access Pattern Analysis}
We evaluate mem\_trace on synthetic and real kernels. A bank-conflict microbenchmark shows per-warp access patterns and conflict rates within 2\% of hardware counters. In \Cref{fig:observability}, instrumenting GEMM, SpMV, and a 1D stencil adds under 3\% end-to-end overhead; PTX injection remains below 50 \(\mu\)s. mem\_trace also pinpointed a convolution-bank conflict that a simple padding fix resolved for a 12\% gain.

\subsubsection{Programmable UVM Management}\label{sec:eval_uvm}
We evaluate programmable UVM management on workloads with diverse memory access patterns: sequential (vector addition), strided (matrix transpose), and random (graph traversal). We compare three configurations: (1) default NVIDIA UVM with on-demand page migration, (2) static prefetching with manual hints, and (3) \sys with adaptive eBPF-based prefetching and eviction policies.

\Cref{fig:uvm_performance} shows normalized execution time across workloads. For sequential access, \sys achieves 1.8$\times$ speedup over default UVM by prefetching consecutive pages. For strided patterns, \sys learns the stride and prefetches accordingly, achieving 1.4$\times$ speedup. Random access shows modest 1.2$\times$ improvement through working-set tracking and retention of hot pages.

We measure page fault frequency in \Cref{fig:uvm_faults}. Default UVM incurs 15-30K page faults per second depending on workload. \sys reduces this to 5-12K faults/sec (50-65\% reduction) through predictive prefetching. The adaptive policy adds only 2-3\% instrumentation overhead while eliminating the majority of fault-induced stalls.

Memory footprint remains comparable: \sys's prefetching increases GPU memory usage by 10-15\% on average, which is acceptable given the performance gains. For memory-constrained scenarios, we implement a hybrid policy that balances prefetch aggressiveness with available memory, maintaining performance within 5\% of unlimited-memory configuration.

\subsubsection{Fine-grain GPU Scheduler}\label{sec:eval_scheduler}
We evaluate fine-grain scheduling with two policies: priority-based preemption and power-aware throttling. Experiments run on mixed workloads combining high-priority latency-sensitive kernels (real-time video processing) with low-priority throughput-oriented tasks (batch ML training).

\paragraph{Priority-based Preemption}
We compare three approaches: (1) no prioritization (FIFO), (2) stream-level priorities (CUDA native), and (3) \sys warp-level preemption. \Cref{fig:scheduler_latency} plots tail latency (p99) for high-priority tasks. FIFO shows high variance (25-80 ms) due to blocking by long-running kernels. CUDA streams reduce p99 to 15-30 ms but still suffer head-of-line blocking. \sys achieves 5-12 ms p99 latency by preempting low-priority warps at barrier synchronization points, yielding GPU resources within microseconds.

Throughput impact on low-priority tasks is measured in \Cref{fig:scheduler_throughput}. \sys incurs 8-12\% throughput reduction compared to FIFO due to context-switching overhead, but maintains fairness better than CUDA streams (18-25\% reduction) which can starve low-priority work.

\paragraph{Power-aware Throttling}
We implement a thermal-aware scheduler that throttles thread blocks when GPU temperature exceeds thresholds. \Cref{fig:power_throttle} shows power consumption over time during sustained workload. Without throttling, power spikes to 320W with thermal violations. NVIDIA's frequency scaling reduces power to 280W but impacts performance by 20\%. \sys's selective thread throttling maintains 290W average power while reducing performance impact to only 8\%, achieving better performance-per-watt than frequency scaling.

Scheduling decision latency is critical: \sys makes warp-level decisions in 0.3-0.8 \(\mu\)s with 4-6\% overhead. This sub-microsecond response enables fine-grain power management that reacts to thermal events before hardware protection mechanisms trigger.

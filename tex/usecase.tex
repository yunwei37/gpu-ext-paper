\subsection{GPU Memory Tracer}\label{sec:use_case_gpu_memory_tracer}


The GPU Memory Tracer demonstrates how \sys{} can provide fine‐grained, real‐time insight into memory access behavior inside running kernels. 
By instrumenting the core load (LD) and store (ST) instructions in GPU code—via PTX trampolines injected at compile time—our tracer records each memory operation’s address, size, warp ID, SM ID, and timestamp directly into a shared eBPF map. 
In practice, a developer enables MemTrace by specifying the target kernel and mapping expression; at runtime, \sys{} patches in lightweight PTX stubs that log metadata into a shared memory region. 
A user‐space analysis callback then consumes these events with sub‐microsecond latency, computing metrics such as instantaneous bandwidth
\[
  \mathrm{BW}(t)=\frac{\sum_{i: t_i\in[t-\Delta,t]}\mathrm{Bytes}_i}{\Delta},
\]
as well as coalescing ratios and per‐SM contention levels. 
This capability proves invaluable when tuning memory‐bound kernels—developers can, for example, spot unexpected bank conflicts or uncoalesced accesses in a tiled convolution, experiment with varying tile sizes, and immediately observe the impact on conflict rates and throughput without restarting the application.

\subsection{Fair Share Scheduling}\label{sec:use_case_fair_share}

The Fair Share Scheduling leverages \sys{}’s block‐level instrumentation to achieve proportional resource allocation among concurrently running GPU workloads. 
In a shared cluster environment, multiple tenants may submit kernels with heterogeneous characteristics—some compute‐bound, others memory‐bound, and still others exhibiting irregular control flow. 
To prevent any single tenant from monopolizing SM occupancy or memory bandwidth, \sys{} injects PTX trampolines at each CUDA block’s entry and exit, logging per‐block execution durations into the same shared eBPF map used by MemTrace. 
A host‐side scheduler reads these timings at fixed intervals, computes each tenant’s relative progress, and adjusts future block‐launch quotas to equalize effective throughput. 
The result is a near‐ideal fairness index (Jain’s \(F\approx0.96\)) with less than 2 \% scheduling overhead, ensuring that slower kernels no longer penalize other tenants and that overall GPU utilization remains high. 
This dynamic, instrumentation‐driven approach requires no changes to application source code and operates transparently alongside existing CUDA streams and memory management.

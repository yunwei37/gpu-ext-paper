
\section{Implementation}
\label{sec:implementation}

\subsection{Components Overview}

We implemented \sys on Linux 6.15, extending the kernel with a standalone file ($\sim$1 KLOC) that handles hook registration and verifier extensions. Additionally, we integrated lightweight instrumentation ($\sim$100 LOC) into NVIDIA's open GPU kernel modules to expose key memory management and scheduling decision points (\S\ref{sec:impl-host}). Our userspace loader and JIT infrastructure ($\sim$10 KLOC) builds upon bpftime's framework, while an LLVM-based backend ($\sim$1 KLOC) translates the restricted \sys eBPF instruction subset into GPU device code (PTX/SPIR-V).\xiangyu{where should we refer to Sec 5.3?}

\subsection{Host-side Integration}
\label{sec:impl-host}

\sys extends the NVIDIA Open GPU Kernel Modules (Turing, Ampere, Hopper, Blackwell, and newer), specifically instrumenting the UVM module at critical memory-management decision points such as the page fault handler and prefetch logic. At each hook, the driver constructs a compact context containing relevant fields (e.g., region range typically aligned to 2MB GPU physical chunks, VA blocks or 4KB Pages, fault address, block size) and invokes an attached eBPF handler. Each handler returns a small enumerated decision indicating whether to execute the default kernel logic or bypass it with custom behavior. We instrument the lifecycle events of GPU hardware queues, each corresponding to a Time-Slice Group (TSG). The kernel maintains a doubly-linked eviction list, and handlers may reorder regions via provided helpers (\texttt{gdrv\_mem\_list\_insert\_head}/\texttt{tail}), but the kernel retains sole eviction authority under memory pressure.  Specifically, we add hooks at TSG initialization (\texttt{queue\_create}) and teardown (\texttt{queue\_destroy}). The eBPF handlers attached to these hooks configure scheduling parameters such as TSG priority, timeslice duration, and runlist interleave frequency. Additionally, policies can cooperatively preempt active TSGs via the \texttt{gdrv\_sched\_preempt} kfunc, invoking the driver's existing context-switch mechanism. Our kernel module directly extends the standard Linux eBPF verifier by registering GPU-specific attach points and kfunc interfaces. The verifier extension leverages BTF annotations and kfunc type signatures to rigorously enforce type and memory safety, safely exposing critical driver-level actions such as eviction candidate selection and kernel preemption to verified eBPF handlers.

\subsection{GPU Runtime}
\label{sec:impl-gpu}

\paragraph{Code Generation and Binary Trampolines.} When a verified \sys eBPF program is loaded into the kernel, our loader intercepts its bytecode and BTF metadata and forwards them to a userspace backend, which translates the restricted eBPF subset into GPU-executable PTX/SPIR-V code. Before the GPU kernel is running on, \sys dynamically intercepts CUDA runtime APIs to extract kernel PTX, rewrite the PTX code with injected binary trampolines, and load the instrumented kernels back into the runtime without recompilation or restart the application. These trampolines are placed strategically at kernel entry, selected memory instructions, and execution-phase boundaries, constructing minimal runtime contexts with only handler-referenced fields, and inserting lightweight prologue/epilogue logic for SIMT register state preservation. Verified eBPF code executes after launching the GPU kernel, supported by a minimal set of pre-compiled GPU helper functions exposed through verifier-controlled signatures.

\sys implements scheduling policies using persistent GPU worker blocks run as long-lived kernels, with persistent warps repeatedly polling and claiming dynamically assigned logical work units. On Blackwell GPUs, we utilize hardware-supported cluster launch control APIs to manage and dynamically schedule units of work. Each GPU worker repeatedly claims work units, invokes device-side eBPF handlers (executed in dedicated SIMT lanes) to select subsequent tasks, and interacts with the cluster APIs to claim or relinquish tasks. Runtime instrumentation and execution-phase annotations are implemented through previously described binary trampolines. For memory management instrumentation, \sys attaches device-side handlers at specific memory instructions, kernel function boundaries, and tracepoints. Device-side handlers issue lightweight policy hints back to the host driver through helper calls, Unlike eBPF\cite{egpu} that rely on expensive atomic synchronization and fences, \sys{} explicitly avoiding cross-SM synchronization primitives to prevent unnecessary hardware stalls and synchronization overhead.


\paragraph{SIMT-aware Verification Implementation}
\label{sec:impl-verification}

We reuse Linux’s existing eBPF verifier to enforce standard memory safety, bounded loops, and type correctness. To incorporate GPU-specific constraints, we introduce an additional verifier pass at program load time, leveraging explicit BTF metadata annotations that mark warp-uniform fields in hook contexts provided by device helpers. At load time, our verifier extracts these annotations to initialize uniformity tags within its internal register and stack-slot metadata structures. The verification pass performs a dataflow analysis on eBPF bytecode, propagating warp-uniformity through arithmetic, logical, and memory load operations. Each instruction inherits uniformity tags according to its operands and explicitly annotated uniformity declarations in helper and kfunc signatures. Control-flow constraints are enforced by traversing the policy’s CFG and explicitly checking each branch predicate and loop bound: any dependence on lane-varying values triggers immediate rejection. Map-update instructions are similarly validated to ensure warp-uniform keys and values derived either from uniform registers or allowed warp-level reductions. GPU-specific safety constraints are enforced by explicit pattern-matching in verifier instruction checks: GPU-wide barriers, global synchronization primitives, and non-uniform atomic operations are explicitly disallowed. Each hook type also carries explicit resource budgets limiting the number of instructions, helper invocations, and memory operations per instruction. We rely solely on static verification, with no additional runtime sandboxing.

\paragraph{Warp-level Execution Implementation}

Warp-level execution aggregation is realized by inserting lightweight trampolines at kernel entry, synchronization barriers, and critical memory instructions (such as global loads and atomic operations). In each trampoline, per-lane inputs are aggregated using GPU warp-level hardware primitives, specifically \texttt{\_\_ballot\_sync} to gather active lane masks and \texttt{\_\_shfl\_sync} for efficient value reductions. An active warp leader is explicitly selected via \texttt{\_\_ffs(\_\_activemask())}, which executes the scalar eBPF handler exactly once per warp. The warp leader's computed result is subsequently broadcast back to all warp lanes through shuffle instructions. During JIT compilation, we aggressively inline helper functions and map accesses directly into handler code, significantly reducing call overhead. Map operations are further optimized by specializing frequent access patterns and embedding them as direct inlined code paths, minimizing branching and global memory traffic.

\paragraph{Hierarchical Maps and Cross-Domain State}

We use eBPF maps allocated within GPU-accessible memory on host or device as a unified state abstraction shared between host-driver and GPU-device contexts. To eliminate explicit CPU-GPU marshalling overhead, map shards are placed according to a profiling-guided heuristic: cold global state resides in host DRAM and is periodically refreshed from GPU-side snapshots; frequently accessed GPU-intensive state is stored in GPU global memory and asynchronously flushed to host; and extremely hot per-warp or per-SM data is cached directly in GPU shared memory or SM-local storage for minimal latency. Consistency across shards is maintained via snapshot-based aggregation at GPU kernel completion boundaries. A runtime daemon asynchronously flushes GPU-local shards to host-visible canonical map instances, providing coherent snapshots to host-side policies without explicit synchronization overhead. Shard updates occur strictly at warp granularity through warp-leader threads without reliance on heavyweight GPU atomic operations. For example, GPU-side handlers accumulate per-region access counters in warp-local registers, which are aggregated once per warp and stored directly into GPU-local shards. The periodic snapshot flush mechanism then transfers these coherent shards to the host for policy decisions, maintaining eventual consistency and correctness invariants without expensive atomic synchronization.
